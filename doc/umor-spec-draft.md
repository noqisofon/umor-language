# Umor 言語仕様ドラフト

Mind言語（日本語プログラミング言語）から着想を得つつ、独自の設計判断を加えた
VMバイトコード変換処理系 Umor の、これまでの議論に基づく仕様整理。

---

## 1. 字句解析（レキサー）— Mindから継承した部分

### 1.1 送り仮名の正規化

漢字に続くひらがな（送り仮名）は、単語識別の際にすべて無視される。

```
反応し
反応する
反応させる
```

上記3つは正規化後すべて `反応` として扱われ、等価である。

- 頭が平仮名で後半が漢字の単語（例：`ご案内する`）は特殊扱いとなり、
  先頭の平仮名は残される（`ご案内`として認識、`案内する`とは別語）。
- 否定形の送り仮名（`させない` など）は文法エラーとする。

### 1.2 全角/半角・大小文字の同一視

半角カタカナ・半角英数字・記号は全角文字と等価とみなす。
小文字英字と大文字英字も同一視する。

```
VIDEO/8 ＝ video/8 ＝ ＶＩＤＥＯ／８ ＝ ｖｉｄｅｏ／８
```

### 1.3 単語区切り

以下はすべて単語区切り文字として等価に扱う：

- 半角/全角スペース
- TAB
- 半角/全角カンマ（, ，）
- 半角/全角読点（、）

単語間のひらがな（送り仮名相当）は無視されるため、
`赤い色で表示する` と `赤色表示する` は等価。

### 1.4 中点の無視

`トータル・カウント` と `トータルカウント` は等価。

### 1.5 コメント

Mind由来の行コメントに加え、C/C++風のコメント記法もサポートする。

**行コメント**（行末までがコメント）：

- `※`（Mind由来）
- `//`（半角）
- `／／`（全角）

```
※ これはコメント
// これもコメント
／／ これもコメント（全角）
```

1.2節の全角/半角同一視の原則により、`//`と`／／`は同じ記号として
扱われる。

**ブロックコメント**（開始記号から終了記号までがコメント）：

- `/* ... */`（半角）
- `／＊ ... ＊／`（全角）

ブロックコメントは**ネストを許可する**。

```
/* 外側
   /* 内側 */
   まだコメント（外側はまだ閉じていない）
*/
```

開始記号と終了記号で全角/半角が混在すること自体は、1.2節の原則により
構文的にはエラーにならない（`／＊ ... */`のような組み合わせも動作する）。
ただし可読性の観点から、コーディングスタイルとしては
**開始と終了で全角/半角を揃えることを推奨**する
（構文レベルでの強制はしない）。

## 2. 助数詞 — フェーズ1はMind方式の正規化として扱う

### 2.1 用語整理：トークンとワード

以降の説明のため、用語を2つに絞る。

- **トークン**：レキサーが出力する字句解析の最終的な単位
  （正規化を経た後の結果）
- **ワード**：辞書に登録され、実行時に呼び出される処理単位
  （`とは`で定義するもの。多くの場合トークンと1対1で対応するが、
  数値リテラルのように、レキサー内で直接「pushする効果」を
  持つ組み込み扱いのものもある）

「単語」という用語はドラフト内では使わない
（1.1〜1.4節で使われている「単語」は、実質的にはここでいう
トークンと同じ対象を指している）。

**ワードの2区分**：ワードはさらに次の2種類に分かれる。

- **基本ワード**：値の内部表現に直接アクセスする必要がある、または
  既存ワードの組み合わせだけでは表現できない処理。VM/インタプリタ側の
  ネイティブ実装が必須（Rustで直接書く）。例：`複製`（dup）・`取替`（swap）・
  算術演算・`番目`（配列というデータ構造の内部にアクセスするため）
- **標準ライブラリ**：基本ワードの組み合わせだけでUmor自身でも
  定義できる処理。ネイティブ実装は必須ではなく、将来的には
  Umor自身で書かれたコードとして提供してもよい

FORTH（ANS Forth / Forth 2012）における Core word set と
Core extension word set の区分に相当する。FORTHでも`CASE`・`PICK`
のような便利ワードはCore wordsの組み合わせでFORTH自身によって
定義される例があり、Umorの標準ライブラリもこれに倣う。

### 2.2 Mind方式の正規化（フェーズ1で採用）

Mindでは「数字の直後に、空白を挟まず数字でないものが現れたら、
その部分を無視する」という単純な規則で助数詞を読み飛ばす。

```mind
２億円に １００円を 加える　　　　←結果は１０２（円は無視される）
```

Umorのフェーズ1もこれを採用するが、位置づけとしては
**「読み飛ばし処理」というより、1.1節の送り仮名正規化と同種の
正規化ルール**として捉える。

`5`、`5と`、`5番目`は、まず個別にトークン化されてから
一部が捨てられるのではなく、**レキサーの正規化処理によって
最初から同一の1個のトークンに畳み込まれる**（現時点ではすべて
`NUMBER(5)`として確定する）。このトークンが実行時に持つ効果は
「`5`をスタックにpushする」だけであり、`と`や`番目`のような
数値への空白なし隣接部分は、独立したトークンとしても
独立したワードとしても、字句解析の出力には一切現れない。

```
5     → NUMBER(5)   （そのまま数値トークン）
5と    → NUMBER(5)   （「と」は数値に空白なし隣接する付属部分として畳み込まれる）
5番目   → NUMBER(5)   （「番目」も同様に畳み込まれる）
```

助数詞専用の宣言構文（`円は 助数詞`）やValue Object化、
型安全性の付与（`5000円 + 3ドル`の検出等）は**フェーズ2以降に先送り**。
理由は、値システムに単位付き型を持ち込むと実装コストが増える一方、
フェーズ1のスコープ（パーサー・基本制御構文）の検証には不要なため。

### 2.3 正規化の判定は字面のみで決まる（辞書引き不要）

数値への付属部分を畳み込むかどうかの判定は、**数値トークンへの
空白なし隣接**という表層パターンのみで決まる。対象の文字列が
将来ワードとして定義される予定かどうかは一切関係しない。

```
5000円    → NUMBER(5000)          （「円」は畳み込まれる）
1番目     → NUMBER(1)             （「番目」も同様に畳み込まれる）
1 番目    → NUMBER(1), WORD(番目)  （空白を挟むと別トークンになる）
```

### 2.4 空白は常にただの区切り文字（特別な意味論ではない）

上の`1番目`と`1 番目`の違いは、**空白自体が特別な意味を
持っている**からではない。

空白の役割は1.3節で述べた通り、他の区切り文字（TAB・カンマ・
読点）と同格の**トークン区切り**でしかなく、それ以上でも以下でもない。
Pythonのインデントのようにブロック構造や意味論を規定する
特別な役割は、Umorの空白には一切与えられていない（5.2節参照）。

その上で、2.3節の正規化ルールが「数値トークンへの**空白なし
隣接**」を条件にしているため、**空白を挟むかどうかで、そもそも
レキサーが生成するトークンの個数自体が変わる**。

- `1番目`：空白がないため、レキサーは最初から`NUMBER(1)`という
  1個のトークンとして正規化する（`番目`は独立して現れない）
- `1 番目`：空白で区切られているため、`NUMBER(1)`と`WORD(番目)`
  という2個のトークンが生成される

評価結果の違いは空白そのものの意味論からではなく、
「生成されるトークンの個数が変わる」という通常の帰結として
説明できる。後者の`WORD(番目)`は、独立したトークンとして
生成された結果、通常の分かち書きとして辞書引きされる。

### 2.5 `番目` は助数詞ではなく基本ワード

`番目`は「畳み込まれて消える付属部分」の一種ではなく、
**空白を挟んで独立したトークンとして現れた場合に限り**、
フェーズ1から実装する通常ワードとして辞書引きされ実行される。

```
：〈配列〉 〈インデックス値〉 番目 → 〈要素〉
```

配列というデータ構造の内部表現に直接アクセスする処理であり、
既存ワードの組み合わせでは表現できないため、2.1節の区分では
**標準ライブラリではなく基本ワード**に分類される
（VM/インタプリタ側にネイティブ実装が必要）。

字面が助数詞的な付属部分（数値に隣接しうる非数値トークン）と
似ているため2.3〜2.4のようなトークン化の違いが生じるが、
処理系内部では「正規化によって独立トークンとして残った
WORDトークンを、通常のワードとして辞書引きする」という
一般規則の中で扱われる。`番目`専用の特別なパーサー規則は
存在しない。

## 3. `（）` の意味論 — 添字アクセスの糖衣構文

### 3.1 位置づけ（重要な訂正）

先行ドラフトでは `（）` を「式のグルーピング」＋「多次元インデックスの
カリー化的連続適用」という独立した評価規則として設計していたが、
これは撤回する。

Umorでの添字アクセスは、そもそも `（）` という専用構文なしで、
2.5の基本ワード `番目` を使った通常の分かち書きとして
表現される。

```umor
売り上げの 1 番目
```

`（）` はこの表現に対する**構文糖衣（シンタックスシュガー）**として
のみ存在する。つまり `（）` 自体は独立した評価規則を持たず、
**パース段階で通常の分かち書きへ機械的に展開（脱糖衣）される**。

```
売り上げ（1）
  ↓ 脱糖衣
売り上げの 1 番目
```

この脱糖衣はマクロ展開に近い処理であり、VM/IRのレベルには
`（）`という概念自体が存在しない。IRに現れるのは
「`売り上げ`をpush → `1`をpush → `番目`ワードを呼ぶ」という、
ただの通常のワード呼び出し列だけになる。

### 3.2 多次元配列 — `（）` の連続も同一規則の繰り返し

複数次元のインデックスアクセスも、脱糖衣を繰り返し適用するだけで
説明がつく。新たな評価規則は不要。

```umor
ダンジョンマップ（X軸座標）（Y座標）
  ↓ 脱糖衣（1段目）
ダンジョンマップの X軸座標 番目（Y座標）
  ↓ 脱糖衣（2段目）
ダンジョンマップの X軸座標 番目の Y座標 番目
```

### 3.3 注意：数値リテラルを直接書く場合の空白

`（）`の中に数値リテラルを直接書く場合、脱糖衣後の形は
`〈値〉の 〈数値〉 番目` となるため、2.3〜2.4節の正規化規則が
そのまま適用される。糖衣構文を使う限りは常に数値と`番目`の間に
空白が入る形に展開されるため、`（）`経由であれば
「`番目`が助数詞として読み飛ばされてしまう」問題は発生しない。

## 4. 単語定義の境界

### 4.1 基本構文

```
＜単語名＞とは（または、は）
    ＜定義内容＞
＜任意の飾り語＞こと。（または単に。）
```

構文的に本質的なのは開始キーワード `とは`/`は` と、
終了記号 `。` の2つのみ。`こと`・`である` などは意味を持たない飾り。

### 4.2 局所処理単語 — `。` を付けない特殊ケース

親処理単語の内部に定義される局所処理単語は、
定義の末尾に `。` を **付けない**。

```
親処理とは
    局所処理１とは
        ・・・・・・・・      ← 。なし
    局所処理２とは
        ・・・・・・・・      ← 。なし
    本体とは                 ← 必須のダミー宣言
        ・・・・・・・・
        ・・・・・・・・すること。   ← ここで初めて。
```

**「本体とは」が必須である理由**（重要）：

`。` による終端がない以上、「`とは` の並びがどこまで局所定義の
連鎖で、どこから親処理自身の本体（実行される中身）に切り替わるか」
を判定する手がかりが構文上どこにも存在しない。
`本体とは` は可読性のための飾りではなく、**曖昧性を解消するために
文法上必須のトークン**である。

これにより、パーサーは以下の単純な規則だけで実装できる：

- `とは` トークンが来たら、直前に未クローズの局所定義があれば
  無条件にpopしてから新しい定義をpushする（先読み不要）
- `。` トークンが来たら、現在の定義をpopする

**トップレベルとの境界**：上記のpop規則は「ワード定義読み込みモード」に
入っている間のみ有効。トップレベル（＝定義スタックが空の状態）で
最初に現れる`とは`は、popすべき対象が存在しないため単純にpushのみを行い、
ここでワード定義読み込みモードに入る。以降、モード内で`とは`に
遭遇するたびに前述のLIFO規則（pop→push）が適用され、`。`で
モードを抜けるまで継続する。つまり判定はスタックの空/非空を見るだけで、
先読みや特別な状態フラグを別途持つ必要はない。

### 4.3 設計思想としての一貫性

Mindは全体を通して「文法的な優雅さより、パーサー実装の簡便さ」を
優先する傾向が一貫している：

| 設計判断                           | 目的                                 |
| ---------------------------------- | ------------------------------------ |
| 送り仮名を無視                     | かな漢字変換の揺れを識別対象にしない |
| 助数詞を無条件破棄（Mind）         | 意味解釈を避け機械的処理に徹する     |
| `。`をネストさせず`本体とは`を要求 | 先読み不要な単純パーサー             |
| インデントに意味を持たせない       | 空白の扱いを1種類のルールに統一      |

Umorのフェーズ1は、この「パーサー簡便性優先」の哲学をほぼそのまま
踏襲している。助数詞はMind同様の読み飛ばし方式を採用し、
`（）`も独立した評価規則を持たせず脱糖衣で吸収することで、
パーサーが扱う概念の種類を増やさない設計を保っている。
型安全性やValue Object化といった独自拡張は、フェーズ2以降に
明確に切り分けている（6章参照）。

### 4.4 トップレベルの即時実行式（FORTH流の対話的実行）

FORTHには「コロン定義（`: NAME ... ;`）以外の場所に書かれたワード列は、
その場で即座に実行される」という重要な特徴がある。トップレベルに
`7 3 + .`と書けば、定義なしにその場で計算されて結果が表示される、
という対話的な性質である。

Umorのフェーズ1でも、この性質を踏襲する。**トップレベルには、
ワード定義だけでなく、その場で評価器によって即座に実行される
「式の列」も書けるようにする。**

```umor
「こんにちは、世界！」を 表示する。

挨拶する とは、
    「こんにちは」を 表示する
こと。

「デバッグ中」を 表示する。
```

上記の例で、`挨拶する とは 〜 こと。`は今まで通りワード定義として
辞書に登録されるだけ（実行はされない）。それ以外の`「こんにちは、
世界！」を 表示する。`や`「デバッグ中」を 表示する。`は、
パースされ次第、評価器によってその場で実行される。

**`。`の役割の拡張**：

- トップレベルの式の列も、`。`で終端する
- ワード定義の`body`（本体）の中では、`。`は使用禁止とする

これにより、`。`が現れた時点で「それが閉じる対象は何か」という
曖昧さが生まれない。`。`は常に「今開いている一番外側の塊
（ワード定義、またはトップレベルの式の列）を閉じる」という
1つの意味しか持たない。ワード定義の内部（`body`）に`。`を
書こうとした場合は構文エラーとする。

**判定方法**：パーサーがトップレベルで次の塊を読み始めるとき、
`〈単語〉 とは`または`〈単語〉 は`という並びが先頭に来ていれば
ワード定義として`parse_definition`に進む。そうでなければ
トップレベルの式の列として扱い、`。`が来るまでのトークン列を
`Vec<Expr>`としてパースする。

**パースと実行の統合（「読みながら実行」モデル）**：

トップレベル式を導入したことで、Umorの実行モデルは
「まずソース全体をパースしてASTを作り、その後で実行する」という
2段階分離をやめ、**パースと実行を交互に行う逐次処理**に変える。

```
ソースの先頭から読む
  ↓
次の塊（ワード定義 or トップレベル式）を1つパースする
  ↓
ワード定義なら → 辞書に登録するだけ（実行しない）
トップレベル式なら → 即座に評価器で実行する
  ↓
ソースの終わりまで繰り返す
```

これはバイトコードVMのような「まず全体をコンパイルしてから実行する」
方式とは異なり、素朴なツリーウォークインタプリタの実装においては
自然な選択である。また、この「読みながら実行」モデルは、
ファイル実行だけでなく**REPL（対話環境）とも同じコアループを
共有できる**という利点がある。ファイル実行は「入力ソースが
ファイル全体」、REPLは「入力ソースが1行ずつ届く」という違いに
すぎず、両者は同じ「次の塊を読んで、ワード定義なら登録、式なら
実行する」というループの上に実装できる。

**REPLの終了コマンド**：REPLは`終了`または`さよなら`という入力で
終了する。これはワードとして辞書に登録するのではなく、REPLの
入力ループ自体が特別に扱う制御コマンドとする（`Ctrl+D`によるEOF
入力でも終了できる、という素朴な挙動に加えて、明示的に終了を
指示できる手段を用意する）。

## 5. 制御構文

### 5.1 条件分岐

```
＜条件＞ ならば ＜then節＞ つぎに
＜条件＞ ならば ＜then節＞ そうでなければ ＜else節＞ つぎに
```

- `そうでなければ` は独立したブロック境界ではなく、
  同一 `ならば`〜`つぎに` ブロック内の節切り替えマーカー。
- ブロックを閉じるのは常に `つぎに` の1つだけ。
- ネストの対応付けは単純なLIFOスタックで解決できる
  （`ならば`でpush、`つぎに`でpop、`そうでなければ`はスタック非関与）。

### 5.2 インデントは無意味

```umor
雨降り？ ならば、傘を差し
                 レインコートを着て
                 ブーツを履く
         つぎに
```

改行・字下げの位置は完全に見た目だけの装飾であり、構文的な意味を
持たない。1行に詰めて書いても同一のASTになる。
ブロック境界はすべてキーワード対（`ならば`/`つぎに`等）で決定される。

### 5.3 `終り` — Mind由来、要検討

Mindには文脈により意味が変わる `終り` という制御構文がある：

1. **処理単語（関数）内**：その単語の実行を即座に終了（`return`相当）
2. **トップレベル**：コンパイル自体をそこで打ち切る
   （以降のソースコードは無視される）

Umorへの移植方針（未確定）：
1番目の用法は素直に`return`として採用してよさそうだが、
2番目は現代の言語設計では通常持たせない機能であり、
デバッグ用途以外ではバグの温床になりうるため、
意図的に落とす判断もありえる。

## 6. 全体方針：段階的な型付け（Factorモデル）

Umorが最終的に指向するのは **Factorのような型付きForth** である。
Factor自身も「動的型付けのスタック言語」として始まり、
`declare` や型注釈といった **オプトインの型検査機構** を後から
積み重ねていった経緯があり、Umorもこれに倣う。

現段階（フェーズ1）では、**Mind譲りの緩い文法検査 ＋ Forth的な
動的スタック評価** を優先し、静的型システムは意図的に持たない。
Mindの「整数入力・小数入力」（属性を書かなければ検査されず、
書けば検査される）という任意オプトイン型検査の仕組みが、
この段階移行の先例として参考になる。

| 論点                   | フェーズ1（今：Mind寄り・動的）                                            | フェーズ2（将来：Factor寄り・型付き）                             |
| ---------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 助数詞（`円`等）       | Mind方式で読み飛ばすのみ。宣言構文も型もなし                               | `円は 助数詞`のような宣言構文＋Value Object化＋型シグネチャを検討 |
| `番目`（添字アクセス） | 基本ワードとしてフェーズ1から実装（型情報なし。ネイティブ実装が必須）      | 型シグネチャ（`Array<T>, Int -> T`）を持つメタデータへ拡張        |
| `（）`のアリティ管理   | パース段階での脱糖衣（構文糖衣の展開）で対応。ランタイムの型検査は行わない | コンパイル時の静的型検査でアリティを先に確定                      |
| 型検査全般             | Mind同様「限りなくゆるい」（デフォルトは無検査）                           | 属性宣言のオプトインから始め、将来は型推論も検討                  |

フェーズ1での実装イメージ（型情報なし）：

```
Word("番目", arity_in=2, arity_out=1, action=λ(arr, i). arr[i])
```

型シグネチャは将来型システムを足す際に後付けできる余地を
残しておけば十分であり、今フェーズで先取りして設計する必要はない。

## 7. 値システム（評価器の`Value`型）

### 7.1 配列・文字列は常に参照で扱う

Mind言語には、文字列を「実体（`○○は 文字列実体 長さ △△`、
固定長バッファを値として持つ）」と「参照（`○○は 文字列`、
アドレスとサイズだけを持つ）」の2種類に明示的に分ける構文がある。

Umorのフェーズ1ではこの区別を持ち込まず、**配列・文字列は
常に参照として扱う**、という単一のルールに統一する。

理由：

- 配列やハッシュのような可変長データを値渡し（実体コピー）で
  扱うメリットが薄い。要素数が増えるほどコピーコストが増す
  一方、参照渡しで困る場面は少ない
- Python・Ruby・JavaScriptなど、多くの現代言語も配列・文字列を
  参照型として扱っており、Rustで実装する上でも素直な選択
- Mindの実体/参照の書き分けは、メモリの限られた環境での
  静的なメモリ確保という実装上の都合に由来すると考えられ、
  現代のRust実装でこの制約を引き継ぐ実利は薄い
- 4.3節・6章で一貫してきた「フェーズ1はシンプルさ優先」という
  設計哲学とも合致する

将来的に固定長のバッファ型が必要になった場合は、
`○○は 変数 長さ 10`のような構文をオプトインで追加する余地を
残しておく（6章のFactorモデル同様、段階的な拡張として扱う）。

### 7.2 文字列はイミュータブル

配列は要素の書き換え（`〜番目に 値を いれる`のような操作）を
想定するため、内部可変性を持つ参照型として扱う。

一方、文字列は**イミュータブル**とする。一度作った文字列の中身を
直接書き換えることはできず、新しい文字列が必要な場合は
新しいオブジェクトとして生成する。これにより、文字列は複製の
コストを気にせず自由に共有できる（参照カウントで実体を共有し、
書き手からは値のように振る舞う）。

### 7.3 `Value`型（実装イメージ）

```rust
enum Value {
    Number(i64),
    Bool(bool),
    String(Rc<str>),                  // イミュータブル。常に参照
    Array(Rc<RefCell<Vec<Value>>>),   // ミュータブル。常に参照
    VarRef(VarHandle),                // 変数への参照（7.4節）。VarHandleは変数スロットを指す何か
}
```

- `Number`・`Bool`はスタック上でコピーされる素朴な値（参照を
  意識する必要がない）
- `String`は`Rc<str>`により、複製時も実体は共有され、
  複製コストは参照カウントの増加のみで済む
- `Array`は`Rc<RefCell<Vec<Value>>>`により、複数の変数や
  スタック位置から同じ配列を参照でき（エイリアシング）、
  要素の書き換えは共有された実体に反映される

### 7.4 変数アクセスはFORTH流（`X`は常に参照を積む）

Xは 変数 で宣言した変数`X`を、ワード呼び出し列の中で`X`とだけ
書いた場合、**値ではなく「Xへの参照」がスタックに積まれる**。
これはFORTHの`VARIABLE`が`X`のように書くと常にアドレスを積み、
値の読み書きは`@`（フェッチ）・`!`（ストア）で明示的に行う
という設計を踏襲したもの。

```umor
X を 表示する      ← Xの参照がpushされ、参照がそのまま表示される
                    （＝参照の文字列表現。値の中身ではない）

X を 読み 表示する  ← Xの参照がpushされた後、読 が参照をpopして
                    値をpush、表示する は値を表示する

0 X 入             ← 0をpush → Xの参照をpush → 入 が
                    ( 値 参照 -- ) の順でpopして書き込む
```

**基本ワード`読`・`入`**：

- `読`（読む）：`( 参照 -- 値 )`。参照をpopし、その先の値をpush
- `入`（入れる）：`( 値 参照 -- )`。値と参照の順でpopし、
  参照の指す先に値を書き込む

送り仮名正規化（1.1節）により、`読む`・`読み`はいずれも`読`に
正規化される。`いれる`（全部ひらがな）は1.1節の例外規則により
正規化されず、`入`（`入れる`から送り仮名を削った形）とは
**別の独立したワード**である。基本ワードとして実装するのは`入`の方。

**設計上の注意点**：

- `Value`型に、変数への参照を表すバリアント（例：`VarRef`）を
  追加する必要がある（7.3節の`Value`型を参照）
- `表示する`のような汎用ワードは、渡された値が参照であっても
  自動的に中身を覗きに行かない。**参照はどこまでも参照として
  扱い、値が欲しければ書き手が明示的に`読`を挟む**、という
  一貫したルールを徹底する。ワード側が「賢く」振る舞って
  参照を自動的に解決してしまうと、9章で避けたワードの特殊化
  （個々のワードが暗黙の変換を行う）と同じ問題が生じる

**フェーズ2以降の課題**：`X を 表示する`と書いた場合に自動的に
値を読んでくれる（`読`の呼び出しを省略できる）という書き味の
改善は、9章のイミディエイトワード的なマクロ機構で解決する
可能性がある（`かつ`の例と同種の問題）。フェーズ1では冗長でも
`読`/`入`を明示する書き方を受け入れる。

### 8.1 フェーズ2以降の再検討候補：REPL駆動開発

4.4節でトップレベルの即時実行式とREPLを導入したことで、
Ruby・Smalltalk文化的な「REPLに向かってワードを育てていく」
**REPL駆動開発**がUmorでも可能になる土台ができた。
ワード定義とトップレベル式が自由に混在できるという性質は、
この開発スタイルの前提条件そのものである。

フェーズ2以降で本格的に検討したい機能候補：

- **ワードの再定義**：REPLから既存のワード定義を上書きし、
  その場で挙動を変えられるようにする（現在の実装でも
  `load_definition`が同名ワードを上書きする形になっていれば、
  既にある程度動く可能性がある）
- **定義済みワード一覧の確認**：FORTHの`WORDS`に相当する、
  現在の辞書に登録されているワードを一覧表示するコマンド
- **スタックの中身の確認**：FORTHの`.S`に相当する、現在の
  データスタックの状態をいつでも覗けるコマンド
- **ステップ実行・デバッグ支援**：個々のワードの実行を
  1ステップずつ追える仕組み

これらは今回のスコープ（フェーズ1）には含めず、パーサー・評価器の
基本機能が安定した後、フェーズ2の検討事項として改めて扱う。

### 8.2 フェーズ2以降の再検討候補：Umor自身によるREPL実装

8.1節のREPL駆動開発をさらに一歩進めた構想として、REPLの終了コマンド
（`終了`/`さよなら`）やボキャブラリー（辞書の切り替え）を、
**評価器（Rust側のホスト実装）が特別扱いする制御コマンドとしてではなく、
Umor自身のコードとして記述できるようにする**という方向性がある。

LispやPythonには、REPLとしての振る舞い（プロンプト表示・入力の読み取り・
評価・結果表示のループ）自体を、その言語自身のライブラリコードとして
記述できる伝統がある（Pythonの`code`モジュールなど）。Umorも同様に、
将来的には「REPLらしい振る舞い」自体をUmorコードで記述し、処理系の
上に載せられる余地を残しておきたい。

これは9.4節で触れた「複数フェーズの処理系」や、6.1節のEspri
（VM構築フレームワーク）の構想とも接続する、セルフホスティング寄りの
話である。現時点では方向性の一つとして記録するに留め、具体的な設計
（Rust側とUmor側の役割分担、ボキャブラリー機構の要否など）は
フェーズ2以降、処理系のアーキテクチャがより固まった段階で検討する。

## 9. イミディエイトワード（ユーザー定義マクロ）— フェーズ1では不採用

### 9.1 検討の発端

以下のような、述語を並べて論理演算子で繋ぐ書き方が
自然に読めるのではないか、という発想があった。

```umor
にゃんぷっぷー？とは ぶろぶ？ かつ 猫っぽい？ こと。
```

これは素直なスタック評価としては成立しない
（`かつ`の時点でスタックには述語評価の結果が1個しかなく、
2引数を要求する`かつ`と噛み合わない）。実際にスタック操作として
成立させるには、書き手が明示的に`複製`（dup）・`取替`（swap）を
挿入する必要がある。

```umor
にゃんぷっぷー？とは 複製 ぶろぶ？ 取替 猫っぽい？ かつ こと。
```

### 9.2 検討したアイデアと不採用の理由

上記の変換を`かつ`ワード自身に**コンパイル時に周囲のコード列を
書き換える力**を持たせることで自動化できないか、という案が出た。
FORTHの`IMMEDIATE`ワードに相当する、ユーザーが定義可能な
汎用マクロ機構としてのイミディエイトワードである。

これは**フェーズ1では不採用**とする。理由：

- イミディエイトワードは「コンパイル時」という明確なフェーズ
  （ソース全体を構文木/バイトコードに変換してから実行する）を
  前提にした機構であり、**トークンを読んだそばから逐次実行していく
  インタプリタとは根本的に相性が悪い**
- Umorは最初インタプリタとして動かす方針（1章冒頭の前提）であり、
  「コンパイル時にコード生成を書き換える」という足場自体が
  この段階では存在しない
- 6章で目指す段階的型付け（Factorモデル）とも相性がシビアになる
  （ワード定義側が自由にコード列を書き換えられると、
  将来のスタックエフェクト検査の前提が崩れやすい）

### 9.3 フェーズ1での結論

- ユーザーが「`かつ`と同じ力を持つイミディエイトワード」を
  定義することは**できない**
- `にゃんぷっぷー？`のような定義は、書き手が`複製`/`取替`を
  明示的に書く必要がある
- ただし、`かつ`のような**特定の組み込みワードに限り**、
  インタプリタ側が実行時にスタックの状態を見て親切に
  補ってくれる余地は残しうる（例：`かつ`が実行時に
  スタックの積み上がりを見て、必要なら暗黙に処理する、等）。
  これはユーザー定義可能な汎用マクロ機構とは別物であり、
  個別の組み込みワードの実装詳細として扱う
- イミディエイトワード（汎用メタプログラミング機構）自体は、
  コンパイラのフェーズ（パーサー→AST→IR）が明確になった
  フェーズ2以降に再検討の余地を残す

### 9.4 フェーズ2以降の再検討候補：フェーズ分割された処理系

イミディエイトワードがインタプリタと相性が悪い根本原因は
「コンパイル時」という区切りがUmorに存在しないことだった。
逆に言えば、**LispのマクロやPerlの`BEGIN`ブロックのように、
処理系自体が複数フェーズ（例：読み込み→マクロ展開→評価）を
持つ設計にすれば、イミディエイトワード的な機構も成立しうる**、
という発想がある。

この場合、マクロ展開フェーズで操作対象になるトークン列やASTを
Umor自身の値として表現する必要が出てくる。これは6章末尾で
触れた「共通IRをUmorの値として表現し、バックエンド変換を
Umorで書けるようにする」という拡張性の話とも接続する
（IRだけでなく、ASTやトークン列も同様にUmorの値として
表現できれば、マクロ展開・バックエンド変換の両方が
同じ仕組みの上に乗る）。

ただしこれは処理系の全体アーキテクチャ（インタプリタ／コンパイラの
区別、フェーズの粒度、各フェーズで何がUmorの値として見えるか）に
関わる大きな決定であり、**フェーズ1のスコープには含めない**。
パーサー・型検査・IR設計が進んだ後、フェーズ2の検討事項として
改めて扱う。

### 9.5 フェーズ2以降の再検討候補：イミディエイトワードの名前空間

9.4節のような複数フェーズの処理系を将来導入する場合、
イミディエイトワードと通常のワードをどう共存させるかという
問題が新たに出てくる。例えば`かつ`（論理積）について：

- `かつ`（ひらがな）＝イミディエイトワード
  （9.1節のように、周囲のコード列に`複製`/`取替`を挿入する）
- `且つ`（漢字）＝通常のワード（`and`相当、素直に2値popしてAND）

のように、**表記の違いをそのまま用途の違いとして使い分ける**案がある。

検討した代替案として、イミディエイトワードと通常ワードで
**名前空間自体を分離する**（同じ文字列`かつ`をイミディエイトとしても
通常ワードとしても同時に定義でき、パーサーが文脈で使い分ける）
という案も出たが、これは不採用とする。理由：

- 名前解決のロジックが二重になり、「今どちらの名前空間を
  見るべきか」を文脈から判定する必要が生じる。これは4.2節で
  重視してきた「先読み不要な単純パーサー」という設計哲学と衝突する
- 同じ文字列が2つの異なる意味を持ちうること自体が、
  コードを読む人間にとって紛らわしい（`かつ`という字面を見ても、
  それがイミディエイトか通常のワードかは文脈依存になってしまう）

**フェーズ2以降での方針（暫定）**：名前空間は分離せず、
表記の違い（`かつ`/`且つ`のような字面のペア）で
イミディエイトワードと通常ワードを区別する。
ただし「表記のペアをどう選ぶか」という命名規約自体は
未検討であり、これも合わせてフェーズ2での検討事項とする。
