# ADR-0016: フェーズ2の型アノテーション構文イメージ（構想メモ）— `〈変数名〉 は 〈型名〉の 変数`

## Status

Proposed

## Context

ADR-0015で、変数宣言構文`は`の直前スペース必須ルールを確定させた
議論の延長で、フェーズ2（型アノテーション導入後）に書きたい構文の
イメージが挙がった。

```umor
合言葉 は 文字列型の 変数
```

現行のフェーズ1実装（`try_variable_decl`）は、`は`と`変数`の間に
何も挟まらない、次の固定3トークンパターンのみを認識する。

```umor
合言葉 は 変数
```

`合言葉 は 文字列型の 変数`のように`は`と`変数`の間に型情報
（`文字列型の`）を挟む構文は、現行の固定パターンには一致せず、
実装の拡張が必要になる。これはumor-spec-draft.md 6章で示されている
フェーズ2の方針（Factorモデル、オプトインの型検査機構）の
具体的な一例であり、今すぐ実装するものではないが、方向性として
記録しておく価値があると判断した。

## Decision

（構想メモであり、この場では設計判断も実装も確定させない。
フェーズ2の型アノテーション機構を本格検討する際の出発点として
以下を記録する。）

構文イメージ：

```umor
〈変数名〉 は 〈型名〉の 変数
```

例：

```umor
合言葉 は 文字列型の 変数
```

検討すべき論点として、以下が挙がっている（すべて未決定）。

1. **`の`の構文的地位**：`文字列型の 変数`の`の`は、助数詞まわりの
   `の`（spec draft 3章、`（）`アクセスの`売り上げ（回数 番目）`の
   文脈）と同じ「連結の`の`」として扱えるのか、それとも型注釈専用の
   新しい役割を持たせる必要があるのか。
2. **型名の正体**：`文字列型`は、助数詞（spec draft 2章）と同様に
   「ただのワード」として定義されるものなのか（＝ユーザーが独自の
   型名を`〈型名〉は 型`のような宣言構文で追加できる拡張性を
   持たせるのか）、それとも組み込みの型名の閉じた集合（`文字列型`・
   `整数型`など）から選ぶ固定語彙にするのか。前者はFactorモデルの
   「オプトインで積み重ねる」思想に近いが、実装の複雑度は増す。
3. **`try_variable_decl`のパターン拡張**：現行の固定3トークン
   パターン（`Word, は, 変数`）に、型名を挟む可変長パターン
   （`Word, は, 〈型名列〉, の, 変数`）をどう追加するか。
   構造キーワードのマッチングロジック全体への影響を検討する必要が
   ある。
4. **型なし宣言との共存**：`合言葉 は 変数`（型指定なし、フェーズ1
   互換）と`合言葉 は 文字列型の 変数`（型指定あり）は、フェーズ2
   移行後も両方書けるべきか。spec draft 6章の「オプトイン」方針
   （属性を書かなければ検査されず、書けば検査される）に従えば
   両立は前提になるはずだが、パーサーが両方のパターンを区別なく
   受理できる文法設計が必要になる。

## Consequences

**得られるもの（想定）**：

- フェーズ2設計に着手する際、変数宣言の型アノテーション構文について
  ゼロから考え直す必要がなく、既に挙がっている論点（`の`の役割、
  型名の正体、パターン拡張、オプトイン共存）から検討を始められる。

**トレードオフとして受け入れるもの**：

- 本ADRは決定を何も含まない構想メモであり、単体では実装の
  指示書にはならない。フェーズ2の型アノテーション機構全体を
  設計する際に、他の型付け対象（助数詞の型シグネチャ、処理単語の
  引数・戻り値の型など）と合わせて改めて本格的なADRを立てる
  必要がある。
