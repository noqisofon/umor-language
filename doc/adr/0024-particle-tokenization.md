# ADR-0024: 助詞の切り出し機構 — 名詞・変数名への膠着した助詞を独立トークンとして分離する

- Status: Accepted

## Context

次のようなワード列を書きたい、という動機から本ADRの検討が
始まった（`ほげ`は変数）。

```
ほげに 42を 入れる。
```

現行の字句解析ルール（送り仮名正規化、spec 1.1節）は「**漢字**に
続くひらがなを送り仮名として削る」という規則であり、`ほげ`のような
**純ひらがな語**に続く`に`はこの規則の対象外である。そのため
`ほげに`は現状、どの正規化ルールにも該当しない未定義ゾーンとなり、
実装依存で次のいずれかになりかねない。

- `ほげに`をひとつなぎの字句として認識し、辞書に存在しない
  `WORD(ほげに)`という未定義トークンになる
- たまたま分割されて動作するが、それを保証する規則が存在しない

ADR-0015では、構造キーワード`は`について同種の「くっつけ書き」を
検討し、「剥がした後に残る部分が本当に正しい名前になる保証がない」
という実装上の困難から、直前スペース必須という妥協に至った。
しかし助詞は`は・が・を・に・へ・と・で・から・より・まで`等の
**有限で明示的な集合**であり、語の末尾一致によって機械的に
切り出せる可能性がある。ADR-0015の`は`のケースとは事情が異なると
見込まれ、ADR-0023（日本語としての自然さを優先する原則）のもとで
実現を検討する価値があると判断した。

検討にあたり、次の3例が判断材料として挙げられた。

```
ほげに 42を 入れる。   （日本語として正しい・意図も正しい）
ほげを 42に 入れる。   （日本語として正しいが、おそらく意図が違う）
ほげく 42で 入れる。   （日本語としておかしい）
```

この3例から、助詞切り出し機構に求められる性質が確認された。

- 助詞リストは有限かつ明示的でなければならない（`く`のような
  非助詞は絶対にマッチしてはならない）
- 切り出しは**構文的に正しいかどうか**のみを判定する。切り出した
  結果の助詞の使い方が意味的に正しいか（1例目と2例目の違い）は
  レキサー・パーサーの責務ではなく、プログラマが文意を正しく
  書く責任として切り分ける
- 助詞リストに一致しない字句（3例目）は、切り出されずに
  未定義トークンのまま構文エラーとして表面化するべきであり、
  これはバグではなく正しい挙動である

## Decision

助詞を独立したトークン種別として認め、以下の方針で切り出しを行う。

1. **適用順序**：送り仮名正規化（漢字語幹の抽出）を先に適用し、
   その後残った字句の末尾が既知の助詞リストと一致するかを
   チェックする、という2段階のパイプラインとする。これにより
   「漢字語幹＋活用語尾」の既存規則と「語幹＋助詞」の新規則が
   競合しない。

   ```
   反応し   → （1段目）反応          （2段目：該当なし）
   ほげに   → （1段目：該当なし）    → （2段目）ほげ ＋ 助詞(に)
   ```

2. **助詞リストは有限集合として明示的に列挙する**：
   `は・が・を・に・へ・と・で・から・より・まで`を初期候補とする
   （最終確定は実装時にADR更新または別途リストアップする）。
   このリストに末尾が一致しない字句は、助詞切り出しの対象外として
   素通しする。

3. **切り出しは構文レベルの操作に留める**：助詞トークンが構文上
   何を意味するか（代入先を示すのか、動作対象を示すのか等）の
   解釈はパーサー・各ワードの実装に委ねる。レキサーは単に
   「語幹トークン＋助詞トークン」に分離するだけで、助詞の
   意味論的な正しさ（`ほげを 42に 入れる`のような、構文的には
   合法だが意図が逆転している書き方）を検出・警告する責務を
   負わない。

4. **助詞リストに一致しない字句は未定義トークンとして扱う**：
   `ほげく`のような字句は、助詞として切り出せる部分がないため
   そのまま1個のトークンとなり、辞書に存在しなければ通常の
   未定義ワードエラーとして扱われる。これは意図された挙動であり、
   特別なエラーメッセージや検出ロジックを追加する必要はない。

## 宿題（未解決事項）

- **助詞リストの最終確定**：初期候補に挙げた10個で過不足がないか。
  複合助詞（`について`・`に対して`等）を含めるかどうかは未検討。
- **既存ワード名との衝突**：助詞リストに追加した文字列が、既存の
  基本ワード・標準ライブラリのワード名の末尾と偶然一致する
  ケースがないか（例：語幹が`〜と`で終わる既存ワードがあれば、
  意図せず助詞として切り出されてしまう）。ADR-0017の基本ワード
  一覧と突き合わせる作業が必要。
- **`から`・`まで`のような複数文字の助詞と、送り仮名の残りカスとの
  誤判定**：2文字以上の助詞候補について、たまたま送り仮名の
  一部として偶然出現する文字列との区別が必要か検討する。
- **助詞トークンの構文上の役割**：パーサーが助詞トークンをどう
  扱うか（無視して語順のみで解釈するのか、助詞の種類に応じて
  意味を変えるのか）は本ADRのスコープ外とし、別途検討する。
  → **解決済み**（2026-09-12）：助詞トークンは `TokenKind::Word` として
  独立して生成され、インタプリタではNOPワードとして登録されているため、
  文法上そのまま通過して動作する。

## 実装状況（2026-09-12）

本ADRおよび ADR-0032（識別子クォート）に基づき、字句解析器（Tokenizer）に
助詞切り出し機構を実装した。

- 助詞リストは `から`, `まで`, `より`（2文字）、`は`, `が`, `を`, `に`, `へ`, `と`, `で`, `も`, `や`（1文字）の12個を最長一致で判定。
- 送り仮名正規化（漢字語幹）の対象外となる純ひらがな単語に対して、末尾の助詞を独立トークンとして分離する。
- 予約キーワード（`とは`, `こと`, `ここから`, `つぎに`, `ならば`, `そうでなければ`, `さもなければ`, `さよなら`）および `〜こと`, `〜とは` で終わる語は保護し、誤切断を防ぐ。
- 純ひらがな語自体の末尾が助詞と一致する場合（「わに問題」）は、ADR-0032 のクォート（`『わに』に`）により安全に回避可能。

## Consequences

**得られるもの**：

- `ほげに 42を 入れる。`のような、日本語として自然な膠着語的書き方が
  可能になる。ADR-0023の原則（実装コストが過大でない限り日本語
  としての自然さを優先する）を、助詞という具体的な文法要素に対して
  実践する最初のケースとなる。
- ADR-0015の`は`とは異なり、助詞という有限集合に対する機械的な
  末尾一致で解決できるため、`は`のケースで直面したような
  本質的な実装困難を回避できる見込みがある。
- 送り仮名正規化と助詞切り出しを2段階のパイプラインとして
  明確に分離することで、既存の正規化ロジックへの変更を
  最小限に抑えられる。

**トレードオフとして受け入れるもの**：

- 助詞リストの確定、既存ワードとの衝突チェックなど、実装前に
  詰めるべき宿題が複数残っている。本ADRは方針の合意に留まり、
  実装可能な仕様として完結していない。
- 「構文的に正しいが意味的に意図と異なる」書き方（`ほげを 42に
  入れる。`のような助詞の付け間違い）を検出する仕組みを持たない
  ため、プログラマの書き間違いが実行時までエラーとして
  表面化しない可能性がある。これは意図された設計判断（レキサー・
  パーサーの責務をあくまで構文レベルに限定する）だが、
  デバッグ体験への影響は今後の運用で観察する必要がある。
