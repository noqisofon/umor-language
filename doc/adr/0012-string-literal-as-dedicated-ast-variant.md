# ADR-0012: 文字列リテラルをASTの独立バリアントとして表現する

## Status

Accepted

## Context

Julesさんによる実装コードレビュー（2026-09週）で、文字列リテラルの
AST上の表現方法について指摘があった。

現在の実装（`src/parser/mod.rs`）は、`TokenKind::StringLiteral(s)`を
`Expr::WordCall(format!("「{s}」"))`として変換している。つまり
文字列リテラルは、AST上では**通常のワード呼び出しと同じ
バリアント**として表現され、鍵括弧付きの特別な名前を持つワード
呼び出しであるかのように偽装されている。

評価器（`src/interpreter/mod.rs`）のdispatch側では、この偽装を
`strip_string_literal`によって検出・復元し、実際には文字列値として
扱っている。

動作自体に誤りはなく、全テスト（101件）は通過しているが、
この設計には以下の性質がある：

- 文字列リテラルという構文的に別種の要素が、`WordCall`という
  意味的に異なる概念（辞書引きによるワード呼び出し）に無理やり
  乗せられている。
- 文字列リテラルの判定が「ワード名の見た目（鍵括弧で囲まれているか）」
  という文字列パターンマッチに依存しており、パーサーと評価器の
  両方に同じ判定ロジック（またはその逆変換）を持つ必要がある。
- 将来、文字リテラル（`Expr::CharLiteral(char)`）のような別種の
  リテラルを追加する場合も、同様の偽装パターンを踏襲するか、
  ここで設計を改めるかの判断を迫られる。

## Decision

（この場でADRを作成する時点では実装への着手は行わない。設計判断
としての方向性のみをここに記録し、実装はClaude Codeへの指示書
作成時に反映する。）

方向性としては、`Expr`列挙型に文字列リテラル専用のバリアントを
追加する案を採用する。

```rust
enum Expr {
    WordCall(String),
    NumberLiteral(i64),
    StringLiteral(String),  // 追加
    IfElse { .. },
    // ...
}
```

- パーサーは`TokenKind::StringLiteral(s)`を`Expr::WordCall`に
  変換せず、直接`Expr::StringLiteral(s)`として構築する。
- 評価器のdispatchは`Expr::StringLiteral(s)`を専用の腕（match arm）
  で処理し、`s`をそのままスタックにpushする。`strip_string_literal`
  による復元処理は不要になる。
- 鍵括弧（`「」`）は構文上の区切り文字として引き続きトークナイザ／
  パーサーで認識するが、AST到達後は「文字列リテラルである」という
  情報が型として保持されるため、実行時に見た目から再判定する
  必要がなくなる。

## Consequences

**得られるもの**：

- AST上で「これは文字列リテラルである」という情報が型として
  明示され、パーサーと評価器の間で判定ロジックの重複や暗黙の
  合意（鍵括弧パターン）に依存しなくなる。
- 将来、文字リテラルなど他のリテラル種別を追加する際に、
  同種の設計（専用`Expr`バリアント）をそのまま踏襲できる、
  一貫した拡張の型が確立される。
- `Expr`をパターンマッチで処理する既存・将来のコード（例えば
  静的解析、フェーズ2の型検査）が、文字列リテラルを`WordCall`と
  取り違える可能性がなくなる。

**トレードオフとして受け入れるもの**：

- `Expr`列挙型・パーサー・評価器の該当箇所を書き換えるリファクタ
  リングコストが発生する（ただし全テストが既に存在するため、
  リグレッションの検知は容易と見込まれる）。
- 現在の実装は動作上の不具合を起こしていないため、この変更は
  純粋に設計の明確化・将来の保守性向上が目的であり、緊急性は
  高くない。実施タイミングは他の作業（評価器・基本ワードセット
  設計）との兼ね合いで決めてよい。
