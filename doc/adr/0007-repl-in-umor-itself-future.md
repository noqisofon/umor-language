# ADR-0007: REPLとしての振る舞いをUmor自身で記述できるようにする（将来検討）

## Status

Proposed（フェーズ2以降の検討事項。今回は方向性の記録のみで、
具体的な設計・実装は行わない）

## Context

ADR-0005・ADR-0006により、UmorのREPLはワード定義とトップレベル式が
自由に混在できる実行コアの上に構築された。これにより、Ruby・
Smalltalk文化的な「REPLに向かってワードを育てていく」REPL駆動開発の
土台ができている。

LispやPythonには、REPLとしての振る舞い（プロンプト表示・入力の
読み取り・評価・結果表示のループ）自体を、その言語自身のライブラリ
コードとして記述できる伝統がある（Pythonの`code`モジュールなど）。
現在のUmorのREPLは、この振る舞いをすべてRust側（ホスト実装）に
持たせている。

## Decision（暫定・未確定）

将来的には、REPLの振る舞い（`終了`/`さよなら`のような制御コマンドの
扱い、ボキャブラリー＝辞書の切り替えなど）を、Rust側の特別扱いでは
なく**Umor自身のコードとして記述できる余地を残す**という方向性を
検討する。

これは以下の既存の検討事項と接続する：

- ADR-0004で触れた、複数フェーズの処理系（読み込み→マクロ展開→評価）
  という、より大きなアーキテクチャ変更の話
- Espri（VM構築フレームワーク、`umor-spec-draft.md` 6.1節）の構想

現時点ではこれらのいずれも具体的な設計に至っていないため、本ADRは
決定ではなく、**検討の方向性のみを記録するもの**とする。

## Consequences

**このADRの位置づけ**：

- 本ADRは「採用」ではなく「将来のフェーズ2で再検討する」ことの
  記録である。フェーズ1の実装には一切影響しない
- ADR-0006で確定した「REPLの終了コマンドは辞書引きの通常ワードとして
  実装する」という設計は、本ADRの検討結果によって変わる可能性がある
  （例えば、辞書の切り替え＝ボキャブラリー機構が入れば、REPL用の
  ワード群を別のボキャブラリーとして分離する、といった発展があり得る）

**再検討時に合わせて検討すべき点**：

- Rust側（ホスト実装）とUmor側のどちらが何を担当するか、役割分担の線引き
- ボキャブラリー機構（複数の辞書を切り替える仕組み）を導入するかどうか、
  導入する場合の設計
- 処理系のアーキテクチャ全体（インタプリタ／コンパイラの区別、
  複数フェーズの導入）との整合性
