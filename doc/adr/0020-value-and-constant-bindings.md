# ADR-0020: アドレスを持たない束縛「可変値」（value）・「定数値」（constant）の導入

## Status

Accepted

## Context

既存の`変数`（variable）はForthの`variable`相当であり、名前を
書くとアドレスが積まれ、中身を読むには別途フェッチ用のワード
（`読む`）を経由する必要がある。値を書き換える際は`入れる`
ワード（Forthの`!`相当）を使う。

一方、Forth系処理系には`variable`とは別に、アドレスを持たず
名前を書いた時点で値そのものが直接スタックに積まれる束縛が
2種類存在する（`VALUE`・`CONSTANT`）。フィボナッチ数実装（ADR-0017
関連の一連の議論）を進める中で、この種の束縛がUmorにまだ存在
しないことが話題になり、導入の検討に至った。

### 3種類の束縛の整理

|                      | `変数`（variable・既存）                   | `可変値`（value）        | `定数値`（constant）     |
| -------------------- | ------------------------------------------ | ------------------------ | ------------------------ |
| アドレスの有無       | あり                                       | なし                     | なし                     |
| 名前を書いた時の動作 | アドレスが積まれる（`読む`で別途フェッチ） | 設定値がそのまま積まれる | 設定値がそのまま積まれる |
| 値の再設定           | 可能（`入れる`でストア）                   | 可能                     | 不可（宣言時のみ）       |

`可変値`と`定数値`の違いは「再設定できるかどうか」の1点のみで
あり、アドレスを持たず名前が直接値に展開されるという性質は
共通する。

## Decision

### 1. 宣言構文

```umor
〈名前〉は 可変値で 〈式〉が 初期値
〈名前〉は 定数値で 〈式〉が 初期値
```

- `可変値`・`定数値`は、既存の`〈名前〉は 変数`と同様の構造
  キーワードパターンの拡張として扱う。
- `初期値`は宣言文の**終端マーカー**として機能する構造キーワード
  である。`可変値で`（または`定数値で`）の直後から`初期値`が
  出現するまでのトークン列を式として評価し、その評価結果
  （宣言時点でのスタックトップの値）を初期値として束縛する。
- `初期値`が終端マーカーであることにより、初期値には単一の
  リテラルだけでなく複数ワードから成る式も指定できる
  （例：`りんごは 可変値で 1 2 加えたものが 初期値`）。これは
  当初の設計案では意図されていなかった副次的な帰結だが、
  自然に得られる利点として採用する。
- 構文上の語順が`可変値で 〈値〉が 初期値`という「値の後にもう
  一度『初期値』という語が続く」形になり、字面上やや冗長である
  ことは認識しているが、`可変値`・`定数値`間で構文パターンを
  完全に統一するための意図的なトレードオフとして受け入れる。

### 2. レキサー・パーサー上の扱い

ADR-0021で明文化した原則の通り、`可変値`・`定数値`・`初期値`は
レキサーレベルでは通常のワードと同一の送り仮名正規化処理を受ける。
構造キーワードとしての意味づけはパーサーの文脈依存の判断としての
み発生する。

### 3. Phase 1における位置づけ

`可変値`・`定数値`の宣言文は、ADR-0010における`回数指定`
〜`繰返す`等と同様、**フェーズ1のインタプリタに限定した特殊構文**
であり、恒久的な言語機能としての構文が確定したものではない。
イミディエイトワード機構導入（ADR-0004参照）以降、将来的に
構文が見直される可能性を残す。

## 今後の検討事項（本ADRのスコープ外）

- **`可変値`の再設定方法**：既存の`入れる`ワード（`変数`用、
  アドレスへのストア）を流用するのか、`可変値`はアドレスを
  持たないため別の専用ワード（例：Forthの`TO`相当）が必要に
  なるのかは未確定。`可変値`はアドレスを持たない設計であるため、
  `入れる`をそのまま適用できない可能性が高く、別途検討が必要。
  → **解決済み**。下記「宿題の解決（2026-09-10実装）」参照。
- **`定数値`の再設定禁止の強制方法**：パーサーレベルで（`定数値`
  として宣言された名前への再設定記述を構文エラーとする）弾くのか、
  実行時エラーとするのか、あるいは強制自体をせず単なる運用上の
  約束事とするのかは未確定。
  → **解決済み**。下記「宿題の解決（2026-09-10実装）」参照。
- **可変値・定数値のスコープルール**：`変数`と同様のスコープ規則
  （ADR-0013関連）に従うのか、別のスコープ規則を持つのかは未検討。
  → **解決済み**。下記「宿題の解決（2026-09-10実装）」参照。
- 本ADRとは別に、Phase 2の型アノテーション構想（ADR-0016）との
  整合性（`可変値`・`定数値`にも将来型情報を付与する可能性）は
  未検討。（引き続き未解決）

## 宿題の解決（2026-09-10実装）

impl-0033にて、上記3つの宿題を以下の通り解決した（ADR-0031で
先に決定されていた「`可変値`の再設定方法は`代入`」を実装に反映
しつつ、残る2つの宿題にも決着をつけた）。

1. **`可変値`の再設定方法**：ADR-0031の決定通り、専用ワード
   `代入`（`〈値の式〉 〈対象名〉 代入`という後置記法）を新設した。
   `変数`用の`入れる`（アドレスへのストア）とは別の機構であり、
   `可変値`はアドレスを持たないため`入れる`の対象にはならない。
2. **`定数値`の再設定禁止の強制方法**：**実行時エラー**
   （`RuntimeError::AssignToConstant`）として実装した。構文
   エラーにしなかった理由は、`可変値`・`定数値`のどちらへの
   `代入`かをパーサーが静的に判別するには、対象名がどちらの
   種類で宣言されたかを追跡する名前解決テーブルをパーサー側にも
   持つ必要があり、実装の複雑さに対して得られる利点（早期検出）が
   小さいと判断したため。
3. **可変値・定数値のスコープルール**：`変数`と同様の親子スコープ
   （子は親を参照でき、兄弟局所処理単語同士は互いに見えない）を
   採用した。ただし`変数`とは独立した別テーブル
   （`Interpreter`の`value_scope_chain`）で管理し、`変数`用の
   `scope_chain`とは混在しない。静的スコープチェック
   （`check_scopes`が兄弟スコープ違反をコンパイル時に検出する
   機能）は、`変数`についても実行はまだ配線されていない
   （ADR-0013参照）ため、`可変値`・`定数値`についても同様に
   未配線のままとした（違反は実行時に`UndefinedWord`として
   検出される）。

詳細な実装内容はADR-0031「実装状況（2026-09-10）」節、および
impl-0033の実装記録を参照。

## Consequences

**得られるもの**：

- Forthの`VALUE`・`CONSTANT`相当の、アドレスを介さない値束縛が
  Umorに追加され、`変数`＋`読む`という2段階アクセスが冗長な
  場面（単純な設定値の参照）でより簡潔な記述が可能になる。
- `初期値`終端マーカー方式により、宣言時の初期値に複数ワードから
  成る式を指定できる、当初想定していなかった柔軟性が得られた。
- ADR-0021の原則に則った設計であることが明示され、今後の
  構造キーワード追加の際の判断基準としても機能する。

**トレードオフとして受け入れるもの**：

- 構文`可変値で 〈値〉が 初期値`は、`定数値で 42が 初期値`のように
  一見「次にまだ値が続くのか」と誤読しうる字面になる。これは
  `可変値`との構文的一貫性を優先した意図的な妥協である。
- 再設定方法・禁止強制方法など、実装に必須ないくつかの詳細が
  本ADRの時点で未確定であり、実装着手前に追加のミニADRまたは
  本ADRの改訂が必要になる可能性が高い。
- `変数`・`可変値`・`定数値`という3種類の束縛が並立することに
  なり、初学者向けにはどれを使うべきかの説明コストが増える
  （ただし、Forth系言語では一般的な区別であり、umor-spec-draft.md
  上での説明整備で対応可能と考える）。
