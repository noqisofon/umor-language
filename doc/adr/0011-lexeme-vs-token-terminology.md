# ADR-0011: 用語定義 — 「字句（lexeme）」と「トークン（token）」を区別する

## Status

Accepted

## Context

`語幹抽出`ワード（未着手・umor-spec-draft.mdの「未解決・要検討事項」に
メモ済み）について議論する中で、次の例における

```umor
「ほげほげを食べる」を 語幹抽出する
```

「`語幹抽出する`のような、**まだ送り仮名正規化を通していない、
ソース上の生の切れ端**」を指す用語が、これまでのADR・spec上に
存在しないことが判明した。

既存のADR・spec draftでは「トークン」という語が既に使われているが
（例：ADR-0002の`NUMBER(1)`,`WORD(番目)`など）、その用法は一貫して
**正規化・分類が完了した後の単位**を指している。一方で「レキサーが
入力から最初に切り出す、まだ正規化前の文字列断片」を指す語が
これまで暗黙のまま会話中で使われており（「単語」「語」などと
曖昧に呼ばれていた）、仕様上の混乱の芽になりうると判断した。

一般的な字句解析（lexical analysis）の用語では、この2つの段階は
明確に区別される：

- **lexeme（字句）**：ソースコード上の生の文字列断片。まだ意味の
  分類も正規化もされていない、切り出されただけの単位。
- **token（トークン）**：lexemeが分類・正規化された結果。種別
  （NUMBER, WORDなど）と正規化済みの値を持つ。

Umorの送り仮名正規化（1.1節、ADR-0010で語幹抽出規則に一般化）は、
まさに「字句 → トークン」の変換の一部である。例えば：

```
字句:     語幹抽出する
          ↓ （送り仮名正規化＝語幹抽出）
トークン: WORD(語幹抽出)
```

## Decision

Umorの仕様・ADR群において、以下の用語を正式に採用する。

- **字句（lexeme）**：レキサーが入力文字列から最初に切り出す、
  正規化前の生の文字列断片。区切り文字（1.3節：スペース・カンマ・
  読点など）による分割直後の状態を指す。
- **トークン（token）**：字句に対して正規化（送り仮名の語幹抽出・
  全角半角統一・助数詞の畳み込み等、1〜2章の各種正規化規則）を
  適用した後の、レキサーの最終出力単位。パーサーはトークン列を
  入力として受け取る。

この区別に従うと、`語幹抽出`ワード（未着手）は「**字句を受け取り、
語幹(文字列)を返す**」ワードとして説明できる。これはレキサー内部の
正規化ロジックを、コンパイル時専用の内部処理ではなくランタイムから
呼び出し可能な形で公開するものであり、独自にUmor VMを実装する人が
自分のレキサー実装の正規化結果を公式仕様と照合するための診断用
ワードとして構想されている（実装は未着手）。

既存のADR・spec draft中の「トークン」という語の用法（ADR-0002等）
はこの定義と矛盾しないため、遡っての修正は不要。今後「正規化前」を
指す必要がある箇所でのみ、新たに「字句」を使う。

## Consequences

**得られるもの**：

- 「正規化前」と「正規化後」を指す語が明確に分離され、今後の
  ADR・spec執筆において「トークン」の一語で両方を曖昧に指して
  しまう混乱を避けられる。
- `語幹抽出`ワードのような、レキサー内部処理をランタイムに公開する
  類のワードを説明する際の語彙が整った。
- 一般的な字句解析の標準用語（lexeme/token）に準拠しているため、
  Umorの実装をForthやMindの実装経験者以外が読む場合にも
  理解のギャップが小さい。

**トレードオフとして受け入れるもの**：

- 「字句」という語自体が日本語の技術文書としてはやや硬い専門用語
  であり、spec全体の平易さとのバランスは今後の執筆で意識する必要が
  ある（無理に多用せず、必要な箇所でのみ使う）。
