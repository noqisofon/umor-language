# ADR-0000: ADRのフォーマットを4段構成にする

- Status: Accepted
- Date: 2026-09-10

## Background

ADRにおける「経緯」の要否について、A氏との間で意見の相違があった。
A氏は ADR を「意思（Decision）だけ書けばよい」という立場で運用している。
一方こちらは、ADR を「その意思に至った経緯が分かればよい」という立場で運用してきた
（[[eris-language]] / [[dim]] などのプロジェクトで実践済み）。

Nygard 原典の ADR フォーマットは Context / Decision / Consequences の三点構造で、
Decision は本来 Context から導かれる帰結として位置づけられている。しかし実務上、
Context という1つのセクションに「なぜこの状況が生まれたか」「具体的に何が起きたか」
「そこからどう判断したか」という異なる種類の情報が全部まとめて放り込まれがちで、
これが Context の曖昧さ・書きにくさの一因になっていた。

## Circumstances

両者の運用の違いを検討した結果、これは優劣ではなく用途の違いだと整理できた。

- **決定ログとしてのADR（A氏）**: 主な読者は「いつ・何が・誰によって決まったか」を
  後から追いたい人。時系列の正確さと、決定が確定した事実であることの記録に価値がある。
- **判断基準の伝達としてのADR（こちら）**: 主な読者は似た状況で次の判断を下す人
  （未来の自分、チームメイト、実装を委託するAI）。判断基準そのものが再利用可能で
  あることに価値がある。

さらに、「未来の自分」も文脈を共有しない他人であるという点に気づいた。3ヶ月後の自分は、
今日の会話も「なんとなくこっちが良さそうという勘」も持っていない。この点で
「未来の自分」と「別セッションのLLM」は、暗黙知の共有がゼロという意味で構造的に
同じ読者である。したがって経緯を書く動機はチーム人数に依存しない。1人プロジェクトでも
半年後の自分に対しては複数人チームと同じ問題が発生する。

昼食の例えで具体化された：
- 意思（Decision）: 「今日は焼きそば！」
- 経緯: 「スーパーの弁当生活をしているが、お弁当はあらかた食べており、
  焼きそばはまだ食べていなかったため選択した」

Decision 単体は具体的すぎて過学習(overfitting)しやすい。次に同じ状況（お弁当の
バリエーションが偏る）に遭遇したとき、「焼きそばを選ぶこと」自体をパターンとして
学習してしまいかねない。本当に汎化されるべきは「消去法で未食のものを選ぶ」という
判断基準の方である。

なお、判断基準は「特に理由はないが、なんとなく選んだ」という形でも構わない。
経緯の価値は「理由の質の高さ」ではなく、「その決定にどれだけ重みを置くべきかを
未来の読者が判定できること」にある。理由を書かずに Decision だけ残すと、
軽い決定すら後から見て過大評価され、不必要に既成事実として神聖視されがちになる。

## Rationale

上記の検討を踏まえ、Context を以下の3つに分解する：

1. **Background** — そもそもなぜこの決定が必要になったか。前提となる状況・制約。
2. **Circumstances** — その時点で具体的に何が起きていたか。選択肢や、
   決定を迫られた直接のトリガー。
3. **Rationale** — Circumstances からどう判断したか。判断基準・優先順位。
   「特に理由なし」もここに正直に書く。

この分解により、以下のようなケースを区別できるようになる：
- 「背景は変わったが理由（判断基準）は変わらない」ケース
- 「背景は同じだが理由が古くなった」ケース

1つの Context にまとめてしまうと、この2つのケースを見分ける手がかりが失われる。

また、Rationale セクションが空・簡潔である（Circumstances から Decision が
自明に導ける）こと自体が「これは軽い決定だった」というシグナルになる。逆に
Rationale が長くなるなら、それは「複数の選択肢が拮抗していた」「トレードオフが
あった」という重要な情報になる。

## Decision

ADR のフォーマットを Background / Circumstances / Rationale / Decision の
4段構成とする。

```markdown
## Background
（そもそもなぜこの決定が必要になったか。前提となる状況・制約）

## Circumstances
（その時点で具体的に何が起きていたか。選択肢や、決定を迫られた直接のトリガー）

## Rationale
（Circumstancesからどう判断したか。判断基準・優先順位。「特に理由なし」もここに正直に書く）

## Decision
（結論。多くの場合、Rationaleから機械的に導出できるはず）
```

Consequences（結果・影響）セクションを別途設けるかどうかは、既存プロジェクト
（[[eris-language]] の ADR 運用など）との互換性を見ながら個別に判断する。
このフォーマット自体、実際に使ってみて書きにくい/読みにくい箇所が出れば
改訂してよい。
