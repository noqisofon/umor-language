# ADR-0026: トップレベルの`変数`宣言をグローバル変数として機能させる

## Status

Proposed

## Context

`variable000.umor`（以下）を実行したところ、パースは通るものの
実行時エラーになることが判明した。

```umor
合言葉は 変数。

「のばら」を 合言葉に 入れる。

合言葉を 読んで 表示する。
```

```
エラー: 実行時エラー: 未定義のワードです: 「合言葉」
```

原因を追ったところ、2層のバグ（というより実装漏れ）が重なっていた。

### 層1：パーサーがトップレベルの変数宣言を認識しない

`Xは 変数`という変数宣言パターンは、通常のワード定義開始パターン
（`Xとは`/`Xは ...`）と字面上区別がつかない。`parse_definition`内部
（局所処理単語・ワード本体の中）では、`try_variable_decl`を
クローズ判定より先に試すことでこの曖昧性を解消しているが、
トップレベルの入口である`parse_top_level_item`にはこのガードが
存在せず、`Xは 変数`が来ると無条件にワード定義の開始として
誤解釈される。

### 層2：インタプリタにトップレベル用の変数フレームが存在しない

仮に層1を解消しても、実行時にはさらに構造的な欠落がある。
変数の実体（`VarSlot`）は`Interpreter::scope_chain`のフレームに
保持されるが、フレームは`Interpreter::call`（＝ワード呼び出し）
経由でしか積まれない。トップレベルの即時実行式
（`TopLevelItem::Expr`）は`call`を経由せず`eval_exprs`を直接
呼ぶだけなので、`scope_chain`に対応するフレームが1つも存在しない。
つまり「変数宣言をどこに登録すればよいか」という受け皿が
トップレベルには最初から用意されていない。

### 設計判断：グローバル変数として許容する

トップレベル変数をワード定義の内部から参照できるようにするか
（＝グローバル変数）、それともトップレベルの式列のみに閉じた
スコープにするかを検討した。Forth系の文化としてはスタック経由の
データ受け渡しが本来の流儀だが、今回は実装の単純さを優先し、
**トップレベル変数はワード定義内からも参照できるグローバル変数として
許容する**という判断とした。

## Decision

### 1. インタプリタ起動時に「土台フレーム」を1つ用意する

`Interpreter::new()`の初期化時に、`scope_chain`へ空の`HashMap`を
1つ、あらかじめpushしておく。このフレームはプログラム実行終了まで
popされない。構造的には`call`が作るフレームと同じものであり、
対応する`Definition`が存在しない点だけが異なる。

`lookup_variable`は`scope_chain`を内側（現在実行中のワード）から
外側へ`rev()`でたどるため、ワード呼び出し中に同名のローカル変数が
あればそちらが優先され、なければ最終的にこの土台フレームまで
探索が落ちてくる。これにより、既存の`lookup_variable`のロジックを
変更せずにグローバル変数の優先順位が自然に成立する。

### 2. パーサーに`Xは 変数`のトップレベル対応を追加する

`parse_top_level_item`が、`peek_word_then_keyword`によるワード定義
開始判定を試みる**前**に`try_variable_decl`を試すよう変更する
（`parse_definition`内部で既に採用している順序と同じ）。

`Xは 変数`にマッチした場合の`Expr`表現として、新たに
`Expr::VariableDecl(String)`バリアントを追加する。`eval_expr`側で
このバリアントを見たら、`scope_chain`の一番底（土台フレーム）に
対して`(name, Rc::new(RefCell::new(None)))`を追加する。

### 3. 再宣言時の挙動

同名のトップレベル変数を再度`Xは 変数`で宣言した場合、
既存スロットを新しい空スロット（`None`）で置き換える（単純な
上書き）。辞書（ADR-0008）のような世代管理は導入しない。
`VarSlot`自体が可変な箱（`Rc<RefCell<Option<Value>>>`）である
ため、世代を分ける実益が薄いと判断した。

## Consequences

**得られるもの**：

- トップレベルで`Xは 変数`と書いたときの直感的な期待（宣言した
  変数がその後のトップレベル式、およびワード定義の中からも
  使える）が満たされる。
- `lookup_variable`・`scope_chain`という既存の仕組みをそのまま
  再利用でき、実装差分が小さい。

**トレードオフとして受け入れるもの**：

- トップレベル変数は実質的なグローバル変数であり、どのワードが
  どの外部状態に依存しているかがコード上見えにくくなる。
  Forth系の「スタック経由でデータを受け渡す」という流儀からは
  外れる。
- ADR-0008の辞書append-only・世代管理という設計思想と、変数の
  単純上書きという挙動が並存することになり、両者の一貫性のなさが
  将来気になる可能性がある。
- ADR-0020（`可変値`/`定数値`）とこの`変数`宣言が将来どう統合
  されるか（`変数`が`可変値`に置き換わるのか、別物として
  共存するのか）は本ADRのスコープ外とし、未解決のまま残す。

## 宿題

- `可変値`/`定数値`（ADR-0020）との統合方針は未検討のまま。
  `変数`宣言が将来的に非推奨化されるのか、共存するのかを
  別途整理する必要がある。
- グローバル変数の再宣言時に警告等を出すかどうかは検討していない
  （現状は無条件で上書き）。
