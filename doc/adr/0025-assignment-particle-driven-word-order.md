# ADR-0025: 代入構文における助詞依存の語順自由化 — `に`・`を`限定、それ以外はデフォルト語順＋警告

## Status

Proposed

## Context

Mind言語では、値を変数に格納する構文は動詞に対する引数の
語順が固定されており、次のような書き方になる。

```
42を ほげに 入れる。   （Mind方式：値→場所→動詞）
```

しかし日本語の会話表現としては、場所を先に言ってから対象を
述べる語順（`ほげに 42を 入れる。`）の方が自然であることが多い。
これはADR-0024（助詞の切り出し機構）の検討中に、そもそも
`ほげに`のような書き方を実現したいという動機から派生した論点
である。

日本語は膠着語であり、助詞が格関係を明示するため、本来は
語順にある程度の自由度がある言語である。ADR-0023（日本語
としての自然さを優先する原則）に照らすと、代入構文についても
「助詞さえ正しければ語順を問わない」という設計が、Forthの
スタック的な語順固定よりも日本語として自然である可能性が
検討された。

対象となる代入操作は、ADR-0017で導入済みの`変数`への`入れる`
（Forthの`!`相当、アドレスへのストア）と、ADR-0020で導入された
`可変値`への再設定（Forthの`TO`相当、ADR-0020の時点では
再設定方法が未確定の宿題として残されていた）の両方を指す。
本ADRはこの再設定ワードの構文解釈について、助詞の観点から
方針を定める。

### 検討過程で確認された具体例

助詞が両方揃っている場合は語順を問わず解釈できる。

```
ほげに 42を 入れる。
42を ほげに 入れる。
```

助詞が片方だけでも、消去法で解釈は一意に定まる。

```
ほげに 42 入れる。      （`に`から場所が確定、残りは値）
ほげ 42を 入れる。      （`を`から値が確定、残りは場所。
                          ただし語順とデフォルト語順が逆転して
                          おり、可読性としてはやや引っかかる）
```

助詞が両方欠落している場合は、一意に解釈する手がかりがない
ため、Mind由来のデフォルト語順（値→場所）にフォールバックする
しかない。

```
ほげ 42 入れる。   → デフォルト語順として「42を ほげに」と解釈
```

さらに、`に`・`を`以外の助詞（`へ`・`から`等）が使われた場合の
扱いも論点となった。

```
ほげへ 42 入れる。         （`へ`は`に`と意味が近いが……）
42から ほげへ 入れる。     （`から`は起点を表す別の助詞）
```

`へ`は`に`と意味範囲が重なる（「ほげへ入れる」は「ほげに入れる」
と読み替え可能）が、代入構文で正式に扱う助詞を増やすほど
判断コストが増える。また`から`は代入文脈よりも「取り出す」系の
操作（`から 取る`等、将来の読み出し系ワードで使われる見込み）
と結びつきやすく、代入構文の解釈に`から`を含めるのは意味的に
無理がある。このため、代入構文で特別扱いする助詞は`に`・`を`の
2つに限定し、それ以外の助詞が使われた場合はデフォルト語順への
フォールバックとして扱うが、単に黙って処理するのではなく、
プログラマの意図しない解釈になっている可能性を知らせるため
警告を出すべきである、という結論に至った。

## Decision

`変数`への`入れる`、および`可変値`への再設定ワード（ADR-0020の
宿題として残っている、名称未定のワード）の引数解釈について、
以下の段階的な規則を採用する。

1. **助詞`に`・`を`が両方とも文中に現れている場合**：助詞のみで
   場所・値それぞれの役割が確定する。語順は問わない。

   ```
   ほげに 42を 入れる。
   42を ほげに 入れる。
   ```
   はいずれも同じ意味として解釈する。

2. **助詞`に`・`を`のどちらか一方のみが現れている場合**：現れて
   いる助詞から一方の役割を確定し、残りの語幹は消去法でもう
   一方の役割として解釈する。語順は問わない。

   ```
   ほげに 42 入れる。
   ほげ 42を 入れる。
   ```
   はいずれも解釈可能とする。ただし後者のように、デフォルト
   語順（規則3）と逆転した並びになる書き方は可読性の観点から
   推奨しないが、構文エラーとはしない。可読性への配慮は
   プログラマの責任とする。

3. **助詞`に`・`を`が両方とも現れていない、または`に`・`を`
   以外の助詞（`へ`・`から`等）が使われている場合**：ADR-0025
   以前のMind由来のデフォルト語順（`値を 場所に`に相当する順序、
   すなわち先に置かれた語を値、後に置かれた語を場所とみなす）
   にフォールバックして解釈する。このとき、`に`・`を`以外の
   助詞が使われている場合は、その助詞が代入構文の解釈に
   使われなかった旨の**警告**を出す（例：「`へ`は代入構文の
   解釈に使われないため、デフォルトの語順として処理しました」）。
   助詞が完全に欠落している場合は警告を出さず、単純にデフォルト
   語順として処理する。

4. **語幹自体が2つの引数として判別できないレベルに構文が
   壊れている場合**（例：`ほげ 42 入`のように、ワード自体が
   辞書に存在しない、または引数の数が合わない場合）：通常の
   構文エラーとする。

## 宿題（未解決事項）

- **`可変値`再設定ワードの正式名称**：ADR-0020から持ち越しの
  宿題。本ADRの助詞解釈規則は名称が何であれ適用される想定だが、
  ワード名自体は別途決定する必要がある。
- **警告の実装方法**：パーサー・インタプリタのどの段階で
  警告を出すか、警告の出力先（標準エラー出力かREPL上の
  メッセージか）は未検討。
- **`へ`を`に`の同義語として正式に吸収するかどうか**：本ADRでは
  `へ`をデフォルト語順＋警告の対象としたが、将来的に`へ`を
  `に`と完全に同一視する（警告なしで受理する）方向に変更する
  可能性は残されている。
- **`変数`と`可変値`とで解釈規則に差を設けるべきか**：本ADRでは
  両者に同じ規則を適用する前提で書いているが、`変数`（アドレス
  あり）と`可変値`（アドレスなし）の実装上の違いが、助詞解釈の
  段階で何らかの区別を必要とするかは未検証。
- **消去法解釈（規則2）の可読性許容範囲**：`ほげ 42を 入れる。`
  のような、デフォルト語順と逆転した書き方をどこまで許容
  すべきかについて、警告を出すべきかどうかも含めて未確定。
  本ADRでは構文エラーにも警告対象にもしていないが、今後の
  運用で見直す可能性がある。

## Consequences

**得られるもの**：

- `ほげに 42を 入れる。`という、日本語として自然な語順での
  代入が可能になる。ADR-0023の原則を代入構文という具体的な
  場面に適用した実例となる。
- 助詞`に`・`を`の役割を明確化しつつ、それ以外の助詞や助詞
  欠落時にも構文エラーで止めるのではなく、デフォルト語順への
  フォールバックと警告という緩やかな失敗モードを用意すること
  で、既存のMind由来の書き方（`42を ほげに 入れる。`）との
  互換性も維持される。
- ADR-0024で定めた助詞切り出し機構の、具体的な利用例が一つ
  確立される。

**トレードオフとして受け入れるもの**：

- 代入構文の解釈規則が4段階の場合分けを持つ、比較的複雑な
  仕様になる。実装・テストの両面でエッジケースの考慮が
  必要になる。
- 助詞`に`・`を`のみを特別扱いし、`へ`・`から`等は警告付きの
  フォールバック対象に留めるという線引きは、直感的にわかり
  やすい一方で、なぜこの2つだけなのかを説明するドキュメントが
  必要になる。
- 消去法解釈（規則2）によって、可読性の低い書き方
  （`ほげ 42を 入れる。`）も構文的には許容されてしまう。
  警告を出さない設計としたため、プログラマがこの書き方に
  気づかないまま使い続けるリスクがある。
