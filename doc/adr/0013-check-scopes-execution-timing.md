# ADR-0013: `check_scopes`（静的スコープチェック）の実行タイミングを明確化する

## Status

Proposed

## Context

Julesさんによる実装コードレビュー（2026-09週）で、静的スコープ
チェック機構の実行タイミングに関する指摘があった。

`src/parser/scope.rs`の`check_scopes`は、局所処理単語間の変数
スコープルール（親の変数は子から参照可、兄弟間アクセス不可、
静的解決— spec draft 該当節）を静的にチェックする機能として
実装されている。

しかし現在の`run_source`は、ソースファイルの**トップレベル要素を
逐次パース・評価**する実装になっているため、`check_scopes`が
呼び出される経路が実装上存在しない、との指摘を受けた。つまり、
違反コードを書いても静的チェックによる検出が実際には機能して
いない可能性がある（テストで直接`check_scopes`を呼んでいる場合を
除き、通常の実行フローでは素通りする）。

これは以下のいずれかを意味する：

1. **未配線のバグ**：本来ファイル実行前に呼ばれるべきだったが、
   実装時に接続し忘れた。
2. **未決定の設計**：`check_scopes`を「言語処理系に組み込まれた
   実行前チェック」にするか、「独立したlinterツールとしてオプトインで
   使うもの」にするか、そもそもまだ方針が決まっていなかった。

いずれであるにせよ、現状では「スコープ違反が静的には検出されず、
実行時に初めて（あるいは実行時にも検出されず単に誤動作として）
問題が顕在化する」という状態であり、放置すべきではない。

## Decision

（この場でADRを作成する時点では実装への着手は行わない。方針の
決定と実装はClaude Codeへの指示書作成時に行う。ここでは論点整理と
暫定的な方針の記録にとどめる。）

以下の2案を比較検討する。

**案A：ファイル実行前の一括静的チェックとして組み込む**

- `run_file`（およびREPLでのブロック単位の定義完了時）において、
  対象のソース全体（あるいは対象の定義単位）をパースした後、
  評価に入る前に`check_scopes`を必ず通す。
- 違反があればコンパイルエラーとして実行そのものを止める。
- Forth系の「読んだそばから逐次実行」という思想とは若干異なる
  （ファイル実行に限っては「まずパースし切ってからチェックし、
  それから評価する」という擬似コンパイルフェーズが必要になる）。
- REPLの対話的な逐次実行（ADR-0005：トップレベル即時実行）とは
  相性を検討する必要がある。1行ずつ即時実行するREPLの性質上、
  「ファイル全体を先読みしてチェックする」という前提を素直には
  持ち込めない可能性がある。

**案B：独立した静的チェックツール（linter）として位置づける**

- `check_scopes`は評価パイプラインの一部としては呼ばれない。
- 別途、CLIサブコマンドやライブラリ関数として明示的に呼び出す
  ものと位置づけ、「実行前に任意でチェックできる道具」として提供する。
- 実行パイプライン自体はシンプルなまま保たれるが、何もしなければ
  スコープ違反は実行時までチェックされない（違反時の実際の挙動
  ―― 誤った変数解決が起きるのか、実行時エラーになるのか ―― は
  別途評価器側の挙動として確認が必要）。

**暫定方針**：ファイル実行（`run_file`）に関しては案Aを基本方針
とする。REPLの逐次実行モードについては、少なくとも「1つの
処理単語定義が`。`で閉じた時点」でその定義単位に対して
`check_scopes`相当のチェックを行う、という粒度で組み込めないかを
実装時に検討する。完全な決定はClaude Codeとの実装作業時に持ち越す。

## Consequences

**得られるもの（想定）**：

- スコープ違反が実行前に検出されるようになれば、兄弟局所処理単語
  からの誤った変数アクセスのような設計上のミスが、実行時の不可解な
  挙動としてではなく、明確なエラーメッセージとして早期に発見できる。
- 「静的チェックとランタイム評価の境界をどこに引くか」という、
  段階的型付け（Factorモデル、spec draft 6章）を目指す上でも重要な
  前例になる。フェーズ2の型検査導入時にも、同様に「いつ静的検査を
  走らせるか」という設計判断が再度必要になるため、ここでの決定が
  参考になる。

**トレードオフとして受け入れるもの（想定）**：

- 案Aを採用する場合、ファイル実行のパイプラインに「全体パース→
  静的チェック→評価」という段階分けが必要になり、現在の逐次的な
  実装よりも構造が複雑になる。
- REPLの対話的即時実行という性質（ADR-0005）と、ファイル単位の
  事前チェックという性質の折り合いをどうつけるか、実装時に
  追加の設計判断が必要になる可能性がある。
