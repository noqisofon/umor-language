# ADR-0018: `【】`（墨付き括弧）記法は言語仕様ではなく開発者間の慣習とする

## Status

Proposed

## Context

`可変値`／`定数値`（VALUE/CONSTANT相当）の設計議論（2026-09-07）の
中で、りひにーさんが例示に`【可】は 定数値、初期値は 真`のような
墨付き括弧`【】`で名前を囲む書き方を使っていた。これは真偽値の
定数など「定数的に扱われるもの」を目立たせるための、りひにーさん
個人の記法（「オレオレ記法」）であることが確認された。

Lispにおける`*special-variable*`のような、いわゆる"earmuffs"命名慣習
（言語のリーダー・コンパイラは特別扱いしないが、開発者コミュニティが
視認性のために用いる命名パターン）に相当するものとして位置づけたい、
という意図が示された。

この記法をUmorの正式構文として採用するかどうかが論点になったが、
りひにーさんは「正式な構文じゃない方が好み」「Umor言語の開発者
（りひにーさん自身）の間でよく使われる慣習にはなるかもしれない」
という方針を明確にした。

さらに、`【】`が変数名・定数名の宣言位置（`〈名前〉は 変数。`等）で
使われた場合に構文上何らかの意味を持つのか（例えば「これは定数だと
パーサーに伝える」といった力を持つのか）が検討されたが、当該位置は
そもそも正規化パイプラインの対象外であり（ADR-0019で確認）、
`【〜】`と書いても`〜`と書いても字句としては同じ扱いになる、という
結論に至った。

## Decision

`【】`（墨付き括弧）記法を、以下の位置づけで採用する。

1. **言語仕様には含めない**：レキサー・パーサーは`【`・`】`という
   文字を一切特別扱いしない。囲まれた内容は、囲みがない場合と
   全く同じようにトークン化される（ADR-0019参照）。`【`・`】`は
   単に識別子・名前の字句に含まれる文字として素通しされる。
2. **開発者間の慣習として運用する**：Umor言語の開発者（現時点では
   りひにーさん）が、定数的に扱われる名前（例：真偽値フラグ、
   変更されないことが期待される値）を可読性のために視覚的に
   目立たせる際に、任意で用いてよい記法とする。Lispの
   "earmuffs"（`*special*`）命名慣習に相当する位置づけである。
3. **パーサーへの実装上の配慮は不要**：`【】`を将来的にも特別な
   構文要素として実装する予定はない。レキサー実装者は`【`・`】`を
   区切り文字（1.3節）や構造キーワードと同様の特別なトークン種別
   として扱わないよう、通常の識別子文字と同じ扱いにしておけば
   十分である。
4. **記録場所**：本記法についての規約は言語仕様書（`umor-spec-draft.md`
   は凍結済み・以降の仕様追記はADRで行う運用のため対象外）には
   記載しない。開発者向けドキュメント（README等、運用フェーズで
   別途整備）に「開発者間の慣習」として触れる程度に留める。

## Consequences

**得られるもの**：

- りひにーさんが今後も`【】`記法を自由に使い続けられる一方で、
  実装側（Claude Code・Jules等）がこれを言語機能と誤解して
  パーサーに特別な分岐を実装してしまうリスクを排除できる。
- 「なぜ`【】`に構文上の力がないのか」の技術的根拠をADR-0019に
  委ねることで、本ADRは運用ルールの記録に専念できる。

**トレードオフとして受け入れるもの**：

- `【】`はあくまで慣習であるため、将来的に別の開発者（人間・AI
  エージェントを問わず）が誤って「特別な意味を持つ構文」だと
  誤解する可能性はゼロではない。誤解が実際に生じた場合は、
  本ADRを実装指示書やコードコメントから参照できるようにしておく
  ことが望ましい。
- 現時点では「定数を目立たせる」という単一の用途のみが確認されて
  いるが、Lispのearmuffs同様、将来的に用途が広がる（例えば別の
  種類のマーカーとして流用される）可能性がある。その場合は本ADRの
  Contextを更新するか、新規ADRを起こすかを都度判断する。
