# ADR-0004: イミディエイトワード（ユーザー定義マクロ）はフェーズ1で不採用

## Status

Accepted

## Context

述語を並べて論理演算子で繋ぐ、次のような書き方が自然に読めるのでは
ないか、という発想が検討の発端だった。

```umor
にゃんぷっぷー？とは ぶろぶ？ かつ 猫っぽい？ こと。
```

しかしこれは素直なスタック評価としては成立しない。`かつ`の時点で
スタックには述語評価の結果が1個しかなく、2引数を要求する`かつ`と
噛み合わない。実際にスタック操作として成立させるには、書き手が
明示的に`複製`（dup）・`取替`（swap）を挿入する必要がある。

```umor
にゃんぷっぷー？とは 複製 ぶろぶ？ 取替 猫っぽい？ かつ こと。
```

この変換を`かつ`ワード自身に**コンパイル時に周囲のコード列を
書き換える力**を持たせて自動化できないか、という案が検討された。
FORTHの`IMMEDIATE`ワードに相当する、ユーザーが定義可能な
汎用マクロ機構としてのイミディエイトワードである。

## Decision

イミディエイトワード（汎用メタプログラミング機構）はフェーズ1では
不採用とする。理由：

- イミディエイトワードは「コンパイル時」という明確なフェーズ
  （ソース全体を構文木/バイトコードに変換してから実行する）を
  前提にした機構であり、トークンを読んだそばから逐次実行していく
  インタプリタとは根本的に相性が悪い。Umorは最初インタプリタとして
  動かす方針であり、「コンパイル時にコード生成を書き換える」という
  足場自体がこの段階では存在しない
- 段階的型付け（Factorモデル）を目指す全体方針とも相性がシビアに
  なる。ワード定義側が自由にコード列を書き換えられると、
  将来のスタックエフェクト検査の前提が崩れやすい

フェーズ1での結論：

- ユーザーが「`かつ`と同じ力を持つイミディエイトワード」を
  定義することは**できない**
- `にゃんぷっぷー？`のような定義は、書き手が`複製`/`取替`を
  明示的に書く必要がある
- ただし、`かつ`のような**特定の組み込みワードに限り**、
  インタプリタ側が実行時にスタックの状態を見て親切に補ってくれる
  余地は残しうる（例：`かつ`が実行時にスタックの積み上がりを見て、
  必要なら暗黙に処理する、等）。これはユーザー定義可能な汎用マクロ
  機構とは別物であり、個別の組み込みワードの実装詳細として扱う

## Consequences

**得られるもの**：

- インタプリタとして素直に動く実行モデルを崩さずに済み、
  フェーズ1のスコープ（パーサー・基本ワードセット）に
  マクロ展開フェーズの設計・実装コストを持ち込まずに済む
- 将来の型検査（スタックエフェクト検査）の前提を、
  ワード定義側からの破壊的な書き換えによって崩される心配なく
  設計できる

**トレードオフとして受け入れるもの**：

- `にゃんぷっぷー？`のような直感的な述語結合の書き方は、
  フェーズ1では`複製`/`取替`を明示的に書く、やや冗長な形でしか
  表現できない
- 汎用メタプログラミング機構自体は、コンパイラのフェーズ
  （パーサー→AST→IR）が明確になったフェーズ2以降に
  再検討の余地を残す。再検討にあたっては、少なくとも次の2点を
  合わせて検討する必要がある：
  - 処理系自体を複数フェーズ（読み込み→マクロ展開→評価）を持つ
    設計に発展させる必要があり、これはインタプリタ／コンパイラの
    区別を含む大きなアーキテクチャ決定になる
  - イミディエイトワードと通常のワードの共存方法（表記の違い
    `かつ`/`且つ`で用途を区別する案が有力候補として残っている。
    名前空間自体を分離する案は、先読み不要な単純パーサーという
    設計哲学と衝突するため不採用と判断済み）
