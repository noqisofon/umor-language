# ADR-0032: 識別子クォート（『』・“”）の導入による助詞衝突の回避と日本語括弧・引用符の役割分担

## Status

Proposed

## Context

ADR-0024（助詞の切り出し機構）および ADR-0025（代入構文における語順自由化）の検討・検証を進める中で、純ひらがなの変数名・ワード名（例：`ほに`、`わに`）に助詞がくっついた場合（`ほにに 42を 入れる` 等）に発生する、字句解析上の本質的な困難が確認された。

Umorにおける既存の正規化パイプラインは、以下の通り「文字種の切り替わり」を境界として利用することで、形態素解析なしに決定論的かつ極めて軽量に処理できている：

1. **漢字語幹 ＋ ひらがな送り仮名**（`入れる` → `入`、`表示する` → `表示`）：
   漢字からひらがなへの文字種変化により、語幹の終わりが明白。
2. **数字 ＋ ひらがな助数詞/助詞**（`42を` → `42`）：
   数字から非数字への文字種変化により、リテラルの終わりが明白（ADR-0002）。

しかし、**純ひらがな語幹 ＋ ひらがな助詞**（例：`ほに` ＋ `に` → `ほにに`、`わに` ＋ `に` → `わにに`）の場合、**文字種の境界が存在しない**。
これを形態素解析なしに「末尾の助詞らしき文字を機械的に切り落とす」という単純なルールで処理しようとすると、語幹自体の末尾が助詞と同じ文字である場合に名前が欠損する（例：変数`わに`が`わ`と`に`に切断され、未定義ワード`わ`になる、通称「わに問題」）。

### 形態素解析を採用しない理由（Forth / Mindの哲学とレトロマシン制約）

この問題を解決するために MeCab や Sudachi 等の日本語形態素解析器を組み込むアプローチは、以下の理由から断固として採用しない：

1. **極小フットプリント・レトロマシンへの移植性の維持**：
   Forth や Mind 言語は、MS-DOS（PC-9801、X68000等）の 640KB メモリ空間やフロッピーディスク 1 枚（1.2MB / 1.44MB）の環境で爆速かつコンパクトに動かすという出自・設計美学を持つ。現代の WebAssembly Playground（ADR-0027）や組み込み・レトロマシン環境を想定した場合、数十MB〜数百MBに及ぶ辞書ファイルと重い解析エンジンは許容できない。
2. **決定論性と予見可能性（Predictability）**：
   辞書の学習コストや更新によって「ユーザーが意図した識別子がどこで切断されるか」が非決定論的に揺らぐことは、プログラミング言語のコンパイラ／インタプリタとして致命的である。コードは誰が見ても完全に予測可能に字句解析されなければならない。

### 解決策としての「識別子クォート（Quoted Identifier）」

SQL の `"column"` や Rust の `r#type` のように、**「普段は言語のルールに従うが、キーワードや助詞と衝突・混同しやすい時だけプログラマが境界を明示的にマークする」** というエスケープ記法は、言語処理系における定石の落としどころである。

日本語の作文習慣においても、固有名詞や紛らわしい名詞をカギ括弧や引用符で括る（例：「『わに』に餌をやる」「“から”を代入する」）ことは極めて自然に行われており、可読性を損なわない。

これに伴い、既存の文字列リテラル（`「」`）や、ADR-0018で「開発者間の慣習（名前に文字として含まれる）」と位置づけられた墨付き括弧（`【】`）との役割分担を明確に整理する必要が生じた。

## Decision

### 1. ワード名（識別子）クォート構文の導入

二重カギ括弧 `『...』` および全角二重カーリー引用符 `“...”` を、識別子の境界を明示するクォート記法として導入する。

```umor
『わに』に 1を 入れる。
“ほに”に 42を 入れる。
```

- **剥がす（含めない）セマンティクス**：
  トークナイザは外側の囲み記号（`『』`、`“”`）を取り除き、中身の文字列のみを語幹トークン（`TokenKind::Word`）として生成する。
  したがって、`わに` と `『わに』` は同一の辞書エントリ（`"わに"`）を参照する。
- **助詞切り出し（ADR-0024）との連携**：
  閉じ記号（`』`、`”`）の直後に空白なしで助詞（`に`、`を`、`は` 等）が膠着している場合、囲みの中身を独立した識別子トークン、直後の助詞を独立した助詞トークンとして確実に分離する。
  これにより、純ひらがな識別子であっても末尾が誤って削られることなく、助詞のみを安全に切り出せる。

### 2. 日本語括弧・引用符記号の包括的な役割分担

Umor における各種日本語括弧・引用符のセマンティクスを以下のように確定し、住み分けを行う：

| 記号 | 種別 | 囲み記号の扱い | 用途・意味 | 備考 |
| :--- | :--- | :--- | :--- | :--- |
| **`「...」`** / **`"..."`**（`＂...＂`） | 文字列リテラル | **剥がす** | テキストデータ（値） | 既存実装通り |
| **`『...』`** / **`“...”`** | **ワード名クォート** | **剥がす** | **識別子エスケープ（助詞衝突回避）** | **本ADRで新規制定** |
| **`【...】`** | 視覚強調ワード名 | **名前に含む** | 定数値等の視覚的強調（Lisp earmuffs風） | ADR-0018通り（通常の識別子文字） |
| **`'...'`**（`＇...＇`） | 文字リテラル | **剥がす** | 1文字データ（値） | 既存実装通り |
| **`（...）`** / **`(...)`** | 添字アクセス糖衣 | **構文変換** | 配列の添字アクセス（ADR-0003） | 既存実装通り |

### 3. ADR-0015（変数宣言の`は`スペース必須）との関係

ADR-0015 では、`Xは 変数` の `は` を切り離す処理が実装困難であったため「スペース必須」という妥協を行った。
本ADRのワード名クォートおよび ADR-0024（助詞切り出し）が導入された後は、`『ほに』は 変数。` や、漢字語幹の `回数は 変数。` のように、空白なしでの宣言構文を自然に解釈できる技術的基盤が完成する。ADR-0015 の制限は、本機構の実装に伴って将来的に段階的緩和（空白なしの容認）が可能となる。

## Consequences

### 得られるもの

- 形態素解析器のような重量級の外部ライブラリ・辞書を一切必要とせず、わずか数行〜数十行のシンプルな決定論的レキサー処理で「純ひらがな＋助詞」の衝突（わに問題）を完全に解決できる。
- フットプリントを極小に保てるため、MS-DOS / PC-9801 等のレトロマシンや WebAssembly（Playground）環境へのポータビリティが維持される。
- 日本語の文章慣習（強調や固有名詞を括弧でくくる）と完全に一致しており、コードの可読性が非常に高い。
- ADR-0018（`【】`は名前に含まれる）の決定を一切覆さず、記号ごとの役割分担が論理的かつ直感的に整理される。

### トレードオフとして受け入れるもの

- 完全な全自動解析ではないため、純ひらがなの変数名に助詞をくっつけたい場合、プログラマが `『』` や `“”` を使って境界を明示するコストを負う（ただし、漢字語幹や数字リテラルではこの明示は不要）。
- レキサーにワード名クォートの認識処理が追加される。
