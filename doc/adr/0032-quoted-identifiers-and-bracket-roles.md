# ADR-0032: 識別子クォート（『』・“”）の導入による助詞衝突の回避と日本語括弧・引用符の役割分担

- Status: Accepted
- Date: 2026-09-12

## Background

Umorは「日本語Forth」として、ForthやMind言語の出自である「極小のフットプリント」「MS-DOS（PC-9801、X68000等）の640KBメモリ空間やフロッピーディスク1枚（1.2MB / 1.44MB）で爆速かつコンパクトに動く」「WebAssembly（ADR-0027 Playground）等の軽量環境でも軽快に動く」という設計哲学・リソース制約を重視している。また、誰が見てもコードの分割結果が完全に予測可能であるという「決定論性（Predictability）」も言語処理系としての根幹にある。

このため、Umorの字句解析パイプラインは形態素解析器（MeCabやSudachi等）に依存せず、以下の通り「文字種の切り替わり」を利用した決定論的かつ超軽量なルールのみで構成されている：

1. **漢字語幹 ＋ ひらがな送り仮名**（`入れる` → `入`、`表示する` → `表示`）：
   漢字からひらがなへの文字種変化により、語幹の終わりが明白。
2. **数字 ＋ ひらがな助数詞/助詞**（`42を` → `42`）：
   数字から非数字への文字種変化により、リテラルの終わりが明白（ADR-0002）。

また、日本語の括弧・引用符記号については、文字列リテラル（`「」`、`"`）や、定数などの視覚的強調のために開発者間の慣習として名前に文字を含める墨付き括弧（`【】`、ADR-0018）が既に存在している。

## Circumstances

ADR-0024（助詞切り出し機構）および ADR-0025（代入構文の語順自由化）の検討・検証の中で、純ひらがなの変数名を用いた以下のコードを実行したところ、実行時エラーが発生した：

```umor
ほに は 変数。
42を ほにに 入れる。
```

```
エラー: 実行時エラー: 未定義のワードです: 「ほにに」
  スタック: [42]
```

この挙動を分析した結果、以下の事実と課題が確認された：

1. `42を` は数値の助数詞畳み込みルール（ADR-0002）により `42` として解釈されスタックに積まれた。
2. しかし `ほにに` は、純ひらがな語幹（`ほに`）＋ひらがな助詞（`に`）であるため**文字種の境界が存在しない**。送り仮名正規化の対象外であり、かつ助詞切り出し機構（ADR-0024）も未実装であるため、丸ごと1つの単語 `WORD("ほにに")` として認識されて未定義エラーとなった。
3. 助詞の前に空白を入れて `42を ほに に 入れる。` と書けば、現状のインタプリタに助詞がNOPワード（`|_interp| Ok(())`）として登録されているため動作する。しかし、「日本語プログラミング言語なのに助詞の前にスペースを強制される」のは日本語として本末転倒である。
4. 一方で、形態素解析なしに「末尾の助詞らしき文字を機械的に切り落とす」ルールを導入すると、単語自体の末尾が助詞と同じ文字である場合に名前が誤って削られる（例：変数`わに`が`わ`と`に`に切断され、未定義ワード`わ`になる、通称「わに問題」）。
5. かといって形態素解析器を持ち込めば、数十MB〜数百MBの辞書が必要となってフロッピーやレトロマシンの極小メモリ空間に入らなくなり、WASM Playgroundの軽量性も損なわれ、辞書による非決定論的な分割事故のリスクを抱え込むことになる。

## Rationale

形態素解析を採用せず、かつ「日本語としての自然さ」と「処理系の軽量性・決定論性」を両立させるため、以下の判断基準・優先順位に基づき検討した：

1. **「9割の自動化 ＋ 1割のエスケープ」という落としどころ**：
   SQLの `"column"` や Rustの `r#type`（Quoted Identifier / Raw Identifier）のように、「普段は言語の自動ルールに任せるが、助詞や予約語と衝突・混同する曖昧なエッジケースだけプログラマが境界を明示する」というエスケープ記法は、言語処理系における最も健全な定石である。
   漢字語幹や数字は文字種境界により完全自動で切り出せるため、純ひらがな語幹で衝突が起きるエッジケースのみ明示マークを付けさせれば十分である。
2. **日本語の文章慣習との調和**：
   日本語の文章作法においても、固有名詞や紛らわしい名詞を括弧や引用符で括る（例：「『わに』に餌をやる」「“から”を代入する」）のは日常的であり、コードとしての視認性・可読性も極めて自然である。
3. **「含まれるかどうか問題」の整理（クォート＝剥がす）**：
   ADR-0018の墨付き括弧`【】`のように囲み記号を名前に含めてしまうと、助詞がない時にも常に囲みを書かなければならず不便が生じる。
   識別子クォートは文字列リテラルと同様に「外側の囲みを剥がして中身だけを名前とする」セマンティクスを採用する。これにより、宣言時や助詞のない呼び出しでは通常の `わに` と書き、助詞が膠着する場面だけ `『わに』に` と安全にエスケープできるようになる。
4. **既存の記号体系との包括的な住み分け**：
   ADR-0018（`【】`は通常の識別子文字として名前に含む）の決定を一切覆すことなく、`『』` / `“”` をクォート（剥がす）専用として位置づけることで、直感的で美しい記号体系が完成する。

## Decision

### 1. ワード名（識別子）クォート構文の導入

二重カギ括弧 `『...』` および全角二重カーリー引用符 `“...”` を、識別子の境界を明示するクォート構文として導入する。

```umor
『わに』に 1を 入れる。
“ほに”に 42を 入れる。
```

- **剥がす（含めない）セマンティクス**：
  トークナイザは外側の囲み記号（`『』`、`“”`）を取り除き、中身の文字列のみを語幹トークン（`TokenKind::Word`）として生成する。
  したがって、`わに` と `『わに』` は同一の辞書エントリ（`"わに"`）を参照する。
- **助詞切り出し（ADR-0024）との連携**：
  閉じ記号（`』`、`”`）の直後に空白なしで助詞（`に`、`を`、`は` 等）が膠着している場合、囲みの中身を独立した識別子トークン、直後の助詞を独立した助詞トークンとして確実に分離する。

### 2. 日本語括弧・引用符記号の包括的な役割分担

Umorにおける日本語括弧・引用符記号のセマンティクスを以下のように確定する：

| 記号                                     | 種別                 | 囲み記号の扱い | 用途・意味                              | 備考                             |
| :--------------------------------------- | :------------------- | :------------- | :-------------------------------------- | :------------------------------- |
| **`「...」`** / **`"..."`**（`＂...＂`） | 文字列リテラル       | **剥がす**     | テキストデータ（値）                    | 既存実装通り                     |
| **`『...』`** / **`“...”`**              | **ワード名クォート** | **剥がす**     | **識別子エスケープ（助詞衝突回避）**    | **本ADRで新規制定**              |
| **`【...】`**                            | 視覚強調ワード名     | **名前に含む** | 定数値等の視覚的強調（Lisp earmuffs風） | ADR-0018通り（通常の識別子文字） |
| **`'...'`**（`＇...＇`）                 | 文字リテラル         | **剥がす**     | 1文字データ（値）                       | 既存実装通り                     |
| **`（...）`** / **`(...)`**              | 添字アクセス糖衣     | **構文変換**   | 配列の添字アクセス（ADR-0003）          | 既存実装通り                     |

### 3. ADR-0015（変数宣言の`は`スペース必須）との関係

ADR-0015 では、`Xは 変数` の `は` を切り離す処理が困難であったため「スペース必須」という妥協を行った。
本ADRのワード名クォートおよび ADR-0024（助詞切り出し）の導入後は、`『ほに』は 変数。` や、漢字語幹の `回数は 変数。` のように、空白なしでの宣言構文を自然に解釈できる技術的基盤が整うため、ADR-0015 の制限は将来的に段階的緩和（空白なしの容認）が可能となる。
