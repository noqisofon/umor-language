# ADR-0030: エイリアス機構（ワード別名）の導入

## Status

Proposed

## Context

ADR-0017の基本ワード棚卸しの過程で、`swap`相当のワードが
`交換`・`取替`の2つ、実装側の判断で重複して追加されていたことが
判明した（ADR-0029参照）。また、フェーズ1のCOREワードセット
整備（ADR-0029）の議論の中で、`nip`相当のワード`取替捨`のような
「動作をそのまま合成語にした命名」は実装として一意に決まる一方、
和語として初見での意味の掴みにくさが残る、という問題も出てきた。

これらはいずれも根が同じで、「同じ動作に複数の呼び方をしたい」
というニーズが繰り返し表面化したものである。ADR-0017は既に
この種の表現揺れの吸収先として「Mind由来のワードエイリアス
機構」を将来検討事項として名指ししていたが（Phase 1では未実装
と記載）、今回この機構自体をフェーズ1に組み込むことを決定した。

Mindには`〈新名〉は 〈既存語〉と 等価。`という構文でエイリアスを
宣言する機能があり、これが着想元である。ただし、Umorでは
「等価」という言葉よりも、機能の意図がストレートに伝わる
「別名」を採用したいという意向があった。

### 構文設計の検討過程

当初、`は`構文（`〈名前〉は 変数`）の型をそのまま流用し、
`〈新名〉は 〈既存語〉の 別名`とする案が検討された。しかし、
これは`は`の右側が可変長パターン（`変数`、`別名`、将来的には
ADR-0016の型注釈`〈型名〉の 変数`）を取ることを意味し、`は`が
担う役割が肥大化しすぎるという懸念が指摘された。`は`を見ただけ
では後続トークンを読むまでどの構文か判別できなくなることは、
パーサーの見通しの良さを損なう。

この懸念を受け、エイリアス宣言専用の新しい構造キーワード`も`を
導入する案が採用された。「新語も既存語の別名（である）」という
日本語としての読みも、「（他にも呼び方があるけど）これも同じ
ものを指す」という緩やかな並立のニュアンスが、`は`の断定的な
言い切りとは異なる形で自然に収まる。

## Decision

### 1. エイリアス宣言構文

```umor
〈新語〉も 〈既存語〉の 別名。
```

例：

```umor
交換も 取替の 別名。
```

`も`を新しい構造キーワードとして導入し、`は`（変数宣言等）とは
独立した構文として扱う。これにより`は`の役割を肥大化させずに
すむ。

### 2. 実装方式

辞書はADR-0008でappend-onlyのリンクリストと決定済みである。
エイリアスは、**既存語と同じ実体（実装・振る舞い）を指す別の
辞書エントリを追加する**ことで実現する。既存語の定義を書き換える
わけではないため、append-onlyの原則と衝突しない。

`交換も 取替の 別名。`を実行すると、辞書に`交換`という新しい
エントリが追加され、そのエントリは`取替`と同じ実装を指す。
以後`交換`と`取替`はどちらも同じ動作をする、辞書上は別々の
エントリとして共存する。

### 3. `交換`/`取替`重複の解決

ADR-0017・ADR-0029で発覚していた`swap`相当ワードの重複を、
本エイリアス機構を使って正式に解決する。`取替`を正式な本体
ワードとし、`交換`はそのエイリアスとする。

```umor
交換も 取替の 別名。
```

これにより、既存コード・既存テストで`交換`を使っている箇所は
そのまま動作し続ける（削除ではなくエイリアス化のため）。

## Consequences

**得られるもの**：

- 表現揺れ（`交換`/`取替`のような同義語）を、正規化ルールを
  無理に一語幹に畳み込むのではなく、明示的な別名関係として
  記録・共存させられるようになる。
- `取替捨`（nip相当）のように「実装として一意だが意味が
  掴みにくい」合成語に対して、将来より直感的な別名を追加する
  余地ができる。
- `は`構文の役割を単純に保ったまま、新しい種類の宣言（エイリアス）
  を追加できた。将来の型注釈構文（ADR-0016）を`は`に押し込む
  かどうかの判断も、今回の`も`分離の前例を参照して検討できる。
- Mindからの継承候補として名指しされていた機能を、Umor独自の
  語彙（「別名」）と構文（`も`）で実現でき、単なる直訳ではない
  形に落とし込めた。

**トレードオフとして受け入れるもの**：

- 構造キーワードが`は`に加えて`も`が増え、フェーズ1の文法が
  ひとつ複雑になる。
- 同じ語に複数回別名を付けられるか（`交換`にさらに別のエイリアス
  を追加できるか）、エイリアスのエイリアスを許すか、といった
  細かい挙動は本ADRでは未検討。
- エイリアス先の語がまだ辞書に存在しない場合のエラー処理
  （前方参照の可否）は未検討。

## 宿題

- エイリアスの多重化（同じ語への複数エイリアス、エイリアスの
  エイリアス）の挙動は未検討。
- エイリアス宣言時に、エイリアス先が未定義だった場合のエラー
  メッセージ・挙動は未検討。
- `取替捨`（nip）等、命名の分かりやすさに課題が残る合成語への
  別名追加は、本ADRでは実施しない。必要になった時点で個別に
  検討する。
- Playground（ADR-0027）上でエイリアス関係をどう見せるか
  （例：ワード一覧に本体とエイリアスの対応を表示するか）は
  未検討。
