# ADR-0019: 正規化パイプラインの適用範囲の再確認と追記 — どこが正規化され、どこがされないか

## Status

Accepted

## Context

これまでのADR群では、送り仮名正規化（ADR-0011で「字句→トークン」
変換として定式化）や述語ワードの`？`正規化、助数詞の数値への
畳み込み（ADR-0002）など、「正規化される」個別のルールがその都度
決定されてきた。一方で「正規化されない」領域については、ADR-0015
（変数宣言の`は`が直前スペース必須であること）のように個別の
文脈で確認されることはあったが、正規化パイプライン全体を俯瞰して
「どこが対象内でどこが対象外か」を一覧化したことはなかった。

`【】`墨付き括弧記法（ADR-0018で扱う、開発者間の慣習的マーカー）が
「変数名・定数名の宣言位置には何の力も持たない」と言えるかどうかを
検討する過程で、この宣言位置（`〈名前〉は 変数。`の`〈名前〉`部分）が
そもそも正規化パイプラインの対象外であることを確認する必要が
生じた。これを機に、既存ADRに散らばっている「される/されない」の
判断を再確認し、一覧として整理しておく。

## Decision

既存ADRの内容を再確認した上で、正規化パイプラインの適用範囲を
以下のように整理する。本ADRは新しい正規化ルールを追加するものでは
なく、既存の決定の棚卸しと、今回新たに確認された1点（変数宣言の
名前部分）の追記である。

### 正規化「される」領域（既存ルールの再確認）

| 対象                     | 正規化内容                                                                            | 出典                      |
| ------------------------ | ------------------------------------------------------------------------------------- | ------------------------- |
| 動詞・述語ワードの活用形 | 送り仮名の語幹抽出（`加える`/`加え`/`加えて`→`加`）                                   | 1.1節、ADR-0010           |
| 述語ワードの`？`         | 非ひらがな文字として扱い`等しい？`→`等？`に正規化                                     | 会話ログ（Key learnings） |
| 数値+助数詞              | 数値トークンへの空白なし隣接文字列を数値トークンに畳み込み（`5000円`→`NUMBER(5000)`） | ADR-0002                  |

これらはいずれも「異なる活用形・表記ゆれを同一語幹に収束させる」
という共通の目的を持つ。ただし過剰正規化（意味の異なる語を同一視
すること、例：`等号`と`均等`を`等`に統合するのは不可）は既存の
Key learningsで明確に禁止されている。

### 正規化「されない」領域（既存ルールの再確認＋今回の追記）

| 対象                                                                 | 扱い                                                                                                   | 出典                                                |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| 構造キーワード直前の名前部分（`ほげほげ とは`の`ほげほげ`）          | 空白区切りでそのままトークン化。送り仮名処理とは無関係                                                 | ADR-0015                                            |
| 変数宣言の名前部分（`ほげほげ は 変数`の`ほげほげ`）**（今回追記）** | 同上。`は`は`とは`と同じ直前スペース必須の構造キーワードであり、名前部分の字句はそのままトークンになる | ADR-0015、本ADRで正規化パイプラインの文脈から再確認 |
| 文字列リテラル（`「」`で囲まれた内部）                               | レキサーが区切り文字による分割自体を行わず、そのまま1トークン                                          | umor-spec-draft.md                                  |

**今回の確認内容**：`ほげほげ は 変数`と書いた場合の`ほげほげ`
部分は、ADR-0015で確定した「`は`は直前スペース必須の構造キーワード」
という前提のもとでは、送り仮名正規化・述語正規化・助数詞畳み込みの
いずれの対象にもならない。**名前として字句がそのまま採用される**
だけであり、正規化パイプライン全体で見ても「対象外」の領域として
扱われていたことを、ADR-0015の文脈（`は`のスペース問題）とは別に、
正規化パイプラインの一覧という観点から再確認した。

この確認は、ADR-0018（`【】`墨付き括弧記法）の前提となる。`【】`が
変数名・定数名の宣言位置で「何の力も持たない」と言えるのは、
その位置がそもそも正規化パイプラインの対象外であり、`【〜】`と
書いても`〜`と書いても字句としては（`【`と`】`の文字を含むか
含まないかを除いて）同じ扱いになる、という本ADRの整理に基づく。

## Consequences

**得られるもの**：

- 「される/されない」の判断が一覧として可視化され、今後新しい
  構文要素（`可変値`／`定数値`の宣言位置、`include`のパス文字列など）
  を追加する際に、正規化パイプラインとの関係を都度確認しやすくなる。
- ADR-0018（`【】`記法）の技術的根拠を本ADRに委ねることで、0018を
  「言語仕様に入れない」という運用ルールの記録に専念させられる。

**トレードオフとして受け入れるもの**：

- 本ADRは「生きた一覧」としての性質を持つ（ADR-0017の基本ワード
  一覧と同様）。新しい構文キーワードが追加されるたびに、この表への
  追記が必要になる。
- 現時点での棚卸しは会話ログとADRの再確認に基づくものであり、
  実装コード（レキサー・パーサーの該当箇所）との突き合わせは
  別途行う必要がある。

## 実装状況・訂正（2026-09-11）

Consequencesで予告されていた「実装コードとの突き合わせ」を実施した結果、後続のADR-0021（構造キーワードのレキサー透過性原則）および実際の実装（`src/tokenizer/mod.rs`）に照らして、本ADRの前提・記述に事実誤認があったことが判明した。経緯の記録として以下に訂正事項を明記した上で、Statusを`Accepted`とする。

### 訂正事項（変数名・ワード名の正規化について）

- **本ADRの記述**: 「変数宣言の名前部分（`ほげほげ は 変数`）や構造キーワード直前の名前は、正規化パイプラインの対象外であり字句がそのままトークンになる」
- **実際の実装（および ADR-0021）**: レキサーは後続のキーワード（`は 変数`や`とは`）を先行判定しないため、変数名・ワード名を含むすべての単語トークンに一律で `normalize_word`（全角半角正規化・大文字小文字正規化・送り仮名除去）が適用される。
  - 例: `X は 変数` の変数名は小文字 `x` に正規化される（`tests/parser_tests.rs` で検証済み）。
  - 例: 漢字＋送り仮名を含む名前（`贈り物 は 変数`）は、語幹 `贈物` に正規化された上で変数名となる。
- **真に正規化パイプラインの「対象外」である領域**:
  - 現状の処理系において正規化を一切受けないのは、**文字列リテラル内部（`「...」` / `"..."`）** のみである。

### ADR-0018（墨付き括弧）への影響

本ADRの主目的であった「`【】`（墨付き括弧）が変数名・定数名の宣言位置で特別な力を持たない」という結論自体は、`【`・`】` がレキサーにおいて通常の文字として素通しされ、正規化後もそのまま識別子文字として保持されることにより、**意図通り正しく成立している**。
