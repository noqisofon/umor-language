# ADR-0017: 基本ワードセットの棚卸しと命名規約

## Status

Proposed

## Context

ADR-0010（ループ構文）の実装過程で、指示書に明記していなかった
基本ワード（`越`＝Forthの`over`相当、`交換`＝`swap`相当）が
実装側（今回はJulesによる実装）の判断で自然発生的に追加された。

これは階乗・フィボナッチ数などRosettaCode由来の実装タスクを
進める中で今後も繰り返されるパターンだと考えられる。個別の
ワード追加のたびにミニADRを起こすのは負荷が高く、追跡漏れの
リスクもあるため、ある時点でのスナップショットとして基本ワード
一覧を棚卸しし、あわせて命名規約を明文化しておく必要が生じた。

### 述語ワード（`？`終わり）の正規化規則

上記の棚卸し作業の過程で、`等しい？`のような述語ワードの語幹が
既存の送り仮名正規化規則（ADR-0010で一般化された「漢字部分を
語幹として抽出し、活用語尾を捨てる」規則）に照らしてどう扱われる
べきかが議論になった。`？`を通常の記号として特別扱いする案、
語幹全体をそのまま保持する案なども検討されたが、最終的に
「`？`を非ひらがな文字（漢字相当）として扱う」という整理に
落ち着いた。詳細は Decision 1節を参照。

### 「基本ワード」と「標準ライブラリ」の区分（既存整理）

umor-spec-draft.mdおよびこれまでの議論で、ワードは以下の2分類が
確認されている。

- **基本ワード**：Rustネイティブ実装が必要なもの（例：`番目`）
- **標準ライブラリ**：基本ワードの組み合わせで表現可能なもの

本ADRは主に前者（基本ワード）の棚卸しを対象とする。

## Decision

### 1. 現時点で確認されている基本ワード一覧

以下は、これまでの設計議論・実装（階乗・フィボナッチ・ADR-0010の
ループ実装）で登場が確認されているワードの一覧である。
**実装コード（Rust側の登録テーブル等）と突き合わせた最終確認は
未完了であり、下表は会話ログとPR概要からの再構成に留まる。**
正確な現状把握のため、実装側（dictionary初期化コード等）を見て
過不足を埋める作業を別途行うこと。

| 表記       | 語幹     | 分類                             | Forth相当         | 出典                             |
| ---------- | -------- | -------------------------------- | ----------------- | -------------------------------- |

**引数順の規約**：2引数を取る算術ワードは、先にpushされた方が第1オペランドになる（`引き`の実測結果：`2 1 引 → 1`、すなわち`a b 引 → a - b`）。`余`もこれに揃え、`a b 余 → a % b`とする（例：`5 3 余 → 2`）。

**スタックシャッフル系ワードの仕様**：`越え`・`交換`・`回転`はいずれもForth相当のスタック操作。`a b 越え → a b a`、`a b 交換 → b a`、`a b c 回転 → b c a`（スタック上位3つを回転し、一番下にあったものが最上位に来る）。

**述語ワードの命名慣習**：`等しい？`のように末尾に`？`を付ける
ワードは、処理系レベルの型強制ではなく、ランタイムスタック上の
bool値で判定される（既存の設計原則、Key learnings参照）。

**述語ワードの語幹は`？`を漢字相当として扱うことで既存規則に
統合される**：`等しい？`はUmorの正規化規則上、`？`を「非ひらがな
文字」（漢字と同格）として扱うことで、通常ワードと同じ一般規則
（漢字部分を語幹として抽出し、活用語尾をすべて捨てる）にそのまま
乗せられる。

具体的には`等しい？`は「`等`（漢字）＋`しい`（送り仮名）＋
`？`（非ひらがな）」という構造として扱われ、`し`・`い`を送り
仮名として除去した結果、**`等？`**に正規化される。同様に
`等しいです？`も`等？`に収束する。一方`等しい`（`？`なし）は
`等`に正規化され、`？`の有無によって述語ワードと非述語ワードが
明確に区別された語幹に収まる。

この扱いは`is_hiragana`判定を変更する必要がなく（`？`はもとより
ひらがな文字ではないため非ひらがな扱いされる）、既存の正規化
ロジックをそのまま適用するだけで実現できる。特別な例外分岐は
不要。

**表現揺れの吸収はエイリアス機構に委ねる（正規化ルールでは
対応しない）**：上記の`？`を漢字相当として扱う規則により、
`等しい？`・`等しいです？`は`等？`に統一される。ただし、これで
すべての表現揺れが解消されるわけではない。たとえば`？`を伴わない
言い切り形のバリエーション（`等しいかどうか`等、`？`を含まない
別表現）までは正規化ルールではカバーしない。

- 正規化ルールを煮詰めて語幹を短く・広く統一するほど、語幹の
  名前空間が狭くなり、意味的に区別したい別ワードが衝突しやすく
  なる（例：`等`まで煮詰めると「等しい」「等号」等が同じ枠を
  取り合う）。**これは仮定の話ではなく、`等号`（記号としての
  equal signを指す名詞）や`均等`（バランスが取れている状態を
  指す語）が、述語ワード`等しい？`とはまったく異なる概念で
  あるにもかかわらず、共通する漢字`等`を含むという理由だけで
  同じ語幹に収束しかねない、という具体的な行き過ぎ事例として
  認識されている。正規化規則は「同じ漢字を含む」だけで語彙を
  まとめるものであってはならず、あくまで活用形の揺れ吸収に
  スコープを限定する。**`？`を漢字相当として扱う今回の規則は、
  `？`という記号自体が独立した語幹要素として保持されるため、
  `等？`（述語）と`等`（非述語）が別語幹に保たれ、この行き過ぎ
  問題を回避できている。
- `？`を含まない表現揺れ（言い切り形のバリエーション等）や、
  意味的に同じだが漢字が異なる表現の統一までは正規化ルールの
  対象外とする。そこまでの揺れ吸収が必要な場合は、Mindから
  継承候補である**エイリアス機構**（ワードに別名を付ける機能、
  Phase 1では未実装）を使い、書き手が明示的に宣言する想定とする。

上記の方針により、述語ワードの主要な表現揺れ（`？`終わりの
バリエーション）は正規化ルールの一般化（`？`を非ひらがな文字と
して扱う）だけで解決される。それ以外の細かい表現揺れは、
エイリアス機構が実装された段階で必要に応じて対応する。

**`可変値`／`定数値`の意味論**：Forthの`VARIABLE`が名前を呼ぶと
アドレスを積む（読み書きは`@`/`!`）のに対し、`VALUE`は名前を呼ぶと
値そのものを積み、書き込みは`TO`相当の専用構文を要する非対称な
ワードである。`CONSTANT`は`VALUE`の不変版（書き込み不可）に相当する。
Umorではこれを`可変値`（`VALUE`相当）・`定数値`（`CONSTANT`相当）
という対の構文キーワードとして訳し分けた。両者とも
`{名前}は {可変値|定数値}で 初期値は {値}`という宣言構文を取る想定
（変数宣言における`は`のアタッチメント問題はADR-0015参照）。
`変数`（`VARIABLE`相当、アドレスを積む）とは字面・意味論とも
明確に区別する。

### 2. 命名規約の観察（Forth用語 → 日本語訳のパターン）

今回の`越`（over）・`交換`（swap）を含め、これまでのForth相当語の
訳し方から、以下の傾向が見て取れる。

- **スタック操作系ワードは、動作の意味を素直に和訳した1〜2字の
  漢語**（`複製`＝dup、`捨`＝drop、`交換`＝swap、`越`＝over）を
  基本とする。
- **算術・比較演算は和語の連用形**（`加え`、`引き`、`掛ける`）を
  用いる。送り仮名正規化により活用形の揺れは吸収されるため、
  `加える`/`加え`/`加えて`のどれで書いても同じ語幹に正規化される
  ことが前提。
- **制御・特殊機能語は熟語**（`再帰`、`打ち切り`）を用いる。
- **変数宣言系の構文キーワードは`{性質}値`の複合語**（`可変値`＝
  `VALUE`、`定数値`＝`CONSTANT`）を用いる。`変数`（`VARIABLE`）とは
  独立した語彙系列とし、一般名詞としての「値」との衝突を避けるため
  この2語は変数宣言構文の決まった位置でのみ用いる想定。

この観察はまだ3〜4例からの帰納に過ぎず、規約として確定させるには
サンプルが不足している。RosettaCodeタスクを通じて新規ワードが
増えるたびに、この規約表を更新し、パターンが安定してきた時点で
正式な命名ガイドラインとして確定させる。

### 3. 今後の運用ルール

- 新しい基本ワードが実装側の判断で追加された場合（今回の
  `越`・`交換`のように、指示書に明記されていない補完的追加を
  含む）、そのつど本ADRの表に追記する。
- 表への追記は原則として軽微な更新として扱い、新規ADRを都度
  起こす必要はない。ただし、命名規約そのものに影響する判断
  （例：新しい命名パターンの導入、既存ワードの改名）が発生した
  場合は、別途ADRを起こして議論する。
- RosettaCodeタスクを一巡した時点で、本ADRの一覧が実装
  （dictionary初期化コード）と完全に一致しているかを棚卸しし、
  Statusを`Accepted`に更新する。

## Consequences

**得られるもの**：

- 実装側（Claude Code・Jules等、複数のエージェントが並行して
  実装を担当しうる状況）が新しいワードを追加する際に参照できる、
  唯一の一覧が確保される。
- 命名規約の傾向が言語化されることで、今後の新規ワード命名時の
  判断コストが下がる。
- 「実装が仕様書より先に進んでしまう」状態（今回の`越`・`交換`の
  ように）が発生しても、事後的に追認・記録する受け皿ができる。

**トレードオフとして受け入れるもの**：

- 本ADRは性質上「生きた一覧」であり、他のADR（決定の記録として
  一度書いたら基本的に変更しない）とはやや異なる運用になる。
  この非対称性を許容する。
- 実装コードとの突き合わせ作業（1節の表の検証）が別途必要であり、
  本ADR自体は現時点では暫定的なスナップショットに過ぎない。
- 命名規約（2節）はサンプル数が少ない段階での帰納であり、
  RosettaCodeタスクが進むにつれて既存の傾向と矛盾する命名が
  出てくる可能性がある。その場合は規約を書き直すことを厭わない。
