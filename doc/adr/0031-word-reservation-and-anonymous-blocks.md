# ADR-0031: ワードの予約・代入と無名ワード（｛｝）— DEFER/IS/:NONAME相当の導入、および可変値の再設定への`代入`統一

## Status

Proposed

## Context

Forthには、ワード名を先に宣言しつつ実行内容を後回しにする`DEFER`、
実行内容を後から差し込む`IS`、現在の内容を取り出す`ACTION-OF`、
そして辞書に名前を残さず値としてのみ存在する無名ワード`:NONAME`
という一群の仕組みがある（iMops-forth @Wikiの解説を参照）。これらは
「前方参照」「相互再帰」「後からの動的な差し替え」といった、通常の
`：定義 ... ；`だけでは書きにくいイディオムを可能にする。

Umorにもこれに相当する機能が必要かどうかを検討した結果、以下の
構文を導入する方向で合意した。

```
ほにを 予約。
ほにに ｛ 「ほに」を 表示 ｝を 代入。
```

`｛ ｝`は無名ワード（Forthの`:NONAME`相当）のリテラルであり、これを
`予約`済みの名前に`代入`することで、DEFER+IS相当の動作を実現する。
将来的には次のような糖衣構文（予約と代入をまとめて書く形）も
検討対象だが、コア機能としては予約・代入・無名ワードの3つで足りる
と考えられる。

```
ほにを ｛ 「ほに」と 表示 ｝として 予約。
```

### `｛ ｝`の意味論

- **グローバルな無名ワードである**。すなわちレキシカルクロージャ
  ではなく、定義時点のローカル変数などを捕捉しない。実行時には
  常に辞書全体（グローバルスコープ）を参照する、通常の名前付き
  ワードと同じ実行環境で動作する。
- **本体構文は名前付き定義と共有する**。すなわち`ほにとは 〜 こと。`
  の「とは」と「こと」の間に書ける内容と、`｛ 〜 ｝`の中に書ける
  内容は完全に同一の文法である。パーサ・コンパイラの本体処理を
  1つに共通化できる。
- 定義完了後、`｛ ｝`はその実行内容を指す**値**（Forthのxt相当）
  として、代入や受け渡しの対象になる。

### 予約ワードを未代入のまま呼んだ場合

`予約`のみを行い、まだ`代入`していないワードを呼び出すと
ランタイムエラーとする。単なる「未定義ワード」エラーとは区別し、
「〈ほに〉は予約されていますが、まだ代入されていません」のような
専用メッセージを表示する。

### ADR-0008との衝突

ここで、既存のADR-0008（辞書は追記のみ・線形リスト方式）との
間に見過ごせない衝突が発覚した。ADR-0008は「定義中の自己参照は、
その定義が辞書に追加される前の時点の辞書状態に対して名前解決
される」と定めている。これは`終了 とは ... 終了する こと。`の
ような自己言及的再定義を正しく動作させるための規則だった。

しかしDEFER/IS的な予約・代入を素朴に「予約＝仮エントリの追記」
「代入＝新エントリの追記（シャドーイング）」として実装すると、
次のようなケースで破綻する。

```
ほにを 予約。
ふがとは ... ほにを 使う こと。       （★）
ほにに ｛ ... ｝を 代入。
```

ADR-0008の規則をそのまま適用すると、（★）の定義本体中に現れる
`ほに`は、「`ふが`という定義が完了する前の時点の辞書状態」に
おける`ほに`、すなわち**予約直後・未代入の`ほに`**に解決されて
しまう。これは代入によって実体が更新された後も、`ふが`は
古い（未代入の）`ほに`を握り続けることを意味し、`ふが`を呼ぶと
常にランタイムエラーになる。

これはDEFER/IS機構が本来解決したい問題（前方参照・後からの
差し替えが、既存の呼び出し元にも反映される）そのものを
無効化してしまう、致命的な組み合わせである。

### ADR-0020の宿題（可変値の再設定方法）との関係

ADR-0020で導入された`可変値`（アドレスを持たず、名前が直接
値に展開される束縛）には、「再設定に既存の`入れる`（`変数`用、
アドレスへのストア）を流用するのか、Forthの`TO`相当の専用ワードが
必要になるのか未確定」という宿題が残されていた。

予約ワードの`代入`を検討する中で、この2つは実は同じ性質の
操作であることに気づいた。予約ワードも可変値も、共通して
「アドレスを介さず、名前が直接指す先の中身を、通常のワード
定義の追記＋シャドーイングとは異なる形で書き換える」という
操作を必要としている。両者の違いは、書き換える中身が
「実行可能なブロック」か「値」かというだけである。

## Decision

1. **`予約`は辞書に新しい種類のエントリ（予約エントリ）を作る**。
   これは通常のワード定義エントリとは別の種類として扱う。
   予約エントリは「名前」と「中身を指す可変スロット」を持ち、
   スロットの初期状態は「未代入」である。

2. **予約エントリはADR-0008のシャドーイング＋追記のルールの
   対象外とする**。すなわち、予約エントリは通常のワード定義の
   ように「新しい定義で辞書に追記され、古い定義が探索順で
   後ろに追いやられる」という扱いを受けない。予約エントリは
   ただ1つだけ存在し、名前解決は常にこの単一のエントリを指す。

3. **`代入`は新しい辞書エントリを追記するのではなく、既存の
   予約エントリのスロットを書き換える（ミューテーションする）**。
   これにより、予約後・代入前に他の定義から`ほに`を参照して
   いた箇所も、代入が完了した時点で新しい中身を指すようになる
   （＝すべての参照が同じスロットを共有する）。

4. **`代入`は再代入可能とする**。一度代入した予約ワードに、
   別の無名ワードを重ねて`代入`することを許可する。これは
   Forthの`IS`が再代入可能であることに倣う。ADR-0008の
   「辞書は追記のみ」という原則は、通常のワード定義（`とは〜こと`）
   にのみ適用され、予約エントリのスロット書き換えには適用
   されない、という形で両者を整合させる。

5. **予約エントリに対して通常の`とは 〜 こと。`で再定義した
   場合の扱いは、本ADRの範囲外とする**（宿題として後述）。

6. **`代入`は予約ワードの再代入と、`可変値`の再設定の両方に
   用いる、共通のワードとする**。ADR-0020で宿題として残されて
   いた「可変値の再設定方法」への回答として、Forthの`TO`相当を
   `代入`が兼ねる。

   ```
   りんごは 可変値で 1が 初期値。
   りんごに 2を 代入。
   ```

   構文上の助詞解釈（`に`・`を`の役割）はADR-0025の規則に
   そのまま従う。可変値の再設定スロットも、予約エントリと
   同様にADR-0008のシャドーイング＋追記則の対象外とし、
   ミューテーションによって書き換える。

7. **`定数値`は`代入`の対象外とする**。`定数値`として宣言された
   名前に対して`代入`を試みた場合の扱い（構文エラーか実行時
   エラーか）は、引き続きADR-0020の宿題として未確定のまま
   残す。本ADRは「`定数値`は`代入`できない」という区別のみを
   確定させ、エラーの種別・検出タイミングには立ち入らない。

## 宿題（未解決事項）

- **予約エントリに対して`とは〜こと。`による通常の再定義を
  行った場合の扱い**：予約エントリと通常定義エントリが同名で
  混在した場合、名前解決やエラー方針をどうするか未検討。
  当面は「予約したワードには`代入`でのみ中身を与える」運用を
  前提とし、`とは〜こと。`による同名の再定義は別ワードとして
  扱う（＝予約エントリとは別に通常のシャドーイングエントリが
  追加され、探索順で優先される）か、あるいはエラーとするかは
  未確定。
- **未代入の予約ワードを呼んだ際の警告表示の要否・実装方法**：
  ランタイムエラーとすることは決定したが、エラーとは別に
  警告ログを残すべきかどうか、出すとしてどの段階（パース時／
  実行時）かは未検討。
- **`ほにを ｛ ... ｝として 予約。`という糖衣構文の正式導入**：
  「予約＋代入」を1文にまとめる構文について、優先度・構文的な
  曖昧性の有無は未検討。導入する場合、内部的には`予約`＋`代入`
  への展開として実装できる見込み。
- **`ACTION-OF`相当（予約ワードの現在の中身を値として取り出す）
  の要否**：Forthでは`DEFER`されたワードの現在のxtを取り出す
  手段が用意されているが、Umorで同等の機能が必要かは未検討。
- **予約エントリのスコープ**：予約は常にトップレベル（グローバル）
  のみで許可するか、ローカルスコープ内での予約も許すかは未検討。
  ADR-0026（トップレベル変数宣言はグローバル）との整合性を
  要確認。
- **`定数値`への`代入`のエラー種別・検出タイミング**：構文
  エラーとして弾くのか、実行時エラーとするのかはADR-0020から
  持ち越しの宿題のまま未確定（Decision 7参照）。
- **`可変値`のスコープと予約エントリのスコープの異同**：両者を
  同じ「ミューテーション可能スロット」という枠組みで扱うことに
  したため、スコープ規則も共通化すべきかどうかは未検討。

## Consequences

**得られるもの**：

- Forthの`DEFER`/`IS`/`:NONAME`に相当する、前方参照・相互再帰・
  動的な差し替えのイディオムがUmorでも書けるようになる。
- 無名ワード`｛ ｝`の本体構文を名前付き定義（`とは〜こと`）と
  完全に共有することで、実装コストと概念数の両方を抑えられる。
- ADR-0008の自己言及的再定義（シャドーイング）の意味論と、
  DEFER/IS的な可変スロットの意味論を、「エントリ種別を分ける」
  ことで矛盾なく共存させられる。
- ADR-0020で宿題として残っていた「可変値の再設定方法」に
  決着がつく。`変数`（アドレスあり・`入れる`）、`可変値`
  （アドレスなし・`代入`）、予約ワード（実行内容の器・`代入`）
  という整理により、`代入`は「アドレスを介さないミューテーション」
  を担う共通ワードとして位置づけられる。

**トレードオフとして受け入れるもの**：

- 辞書の内部構造が「追記専用の通常エントリ」と「ミューテーション
  可能な予約エントリ」の2種類を持つことになり、ADR-0008が
  前提としていた「辞書は単一の意味論（追記のみ）で説明できる」
  というシンプルさが失われる。
- 予約エントリが可変スロットを持つことは、ADR-0008が忌避した
  「上書きによる意図しない副作用」のリスクを、限定的な範囲で
  再び持ち込むことになる。ただし予約エントリは明示的に`予約`
  された名前にのみ生じるため、通常の`とは〜こと`定義には
  影響しない。
- 宿題に挙げた「予約エントリと通常定義の混在」など、詳細な
  エッジケースの仕様がまだ固まっておらず、実装時に追加の
  意思決定が必要になる。
