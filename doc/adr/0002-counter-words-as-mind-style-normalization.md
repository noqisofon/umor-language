# ADR-0002: 助数詞はフェーズ1ではMind方式の正規化として扱う

## Status

Accepted

## Context

助数詞（`円`・`番目`のような、数値に隣接して現れる語）の扱いには、
検討の過程で2つの方式が上がった。

**案A（当初採用・後に撤回）**：助数詞を「スタックから値を1つpopし、
新しいValue Object（`Yen`型など）を構築してpushする、普通の処理単語」
として定義する。`円は 助数詞`のような専用宣言構文を用意し、
`5000円 - 500円`のような演算に型チェックを効かせる、
`5000円 + 3ドル`のような異なる単位間の演算をコンパイル時エラーに
できる、という型安全性のメリットを狙った設計。

この案には`助数詞`という宣言キーワードが「直前の数値トークンに
対して後置形式で振る舞ってよい」というレキサー/パーサーへの
ヒントを与える役割を持たせる必要があり、さらに`番目`のような
「完結型」ではなく「遅延適用型」（1引数を消費して作った値が、
さらに次の値を消費する）の助数詞も存在するため、評価モデルが
2段階に分かれるなど、フェーズ1のスコープに対して複雑さが増していた。

**案B（採用）**：Mind方式をほぼそのまま踏襲し、「数値トークンに
空白なしで隣接する非数値部分は、レキサーの正規化によって
数値トークンに畳み込まれ、独立したトークンとしてもワードとしても
一切現れない」という単純な規則にする。

```
5000円    → NUMBER(5000)          （「円」は畳み込まれる）
1番目     → NUMBER(1)             （「番目」も同様に畳み込まれる）
1 番目    → NUMBER(1), WORD(番目)  （空白を挟むと別トークンになる）
```

この方式では、助数詞専用の宣言構文もValue Objectも型システムも
一切不要になる。判定条件は「数値トークンへの空白なし隣接」という
字面のみで決まり、辞書引きは一切関与しない。

なお、`番目`は「畳み込まれて消える付属部分」ではなく、
**空白を挟んで独立したトークンとして現れた場合に限り**、
フェーズ1から実装する標準ライブラリの通常ワードとして扱う
（辞書引きされて実行される、添字アクセス用のワード）。

## Decision

フェーズ1では助数詞を案Bの方式で扱う。

- 助数詞専用の宣言構文（`円は 助数詞`）、Value Object化、
  型シグネチャの付与は、フェーズ1では持たない
- 数値への正規化は「数値リテラルの直後に空白なしで非数値トークンが
  続く場合、それらをまとめて1個の数値トークンに正規化する」という、
  1.1節の送り仮名正規化と同種の、字面ベースの判定として実装する
- `番目`は例外的に、空白を挟んで独立トークンとして現れた場合に限り、
  フェーズ1の標準ライブラリの通常ワード（添字アクセス）として扱う。
  `番目`専用の特別なパーサー規則は設けない
- 単位付き型による安全性（`5000円 + 3ドル`の検出等）は、
  型システムそのものとあわせてフェーズ2以降で再検討する

## Consequences

**得られるもの**：

- 助数詞のために専用の宣言構文・Value Object・2段階評価モデルを
  実装する必要がなくなり、フェーズ1のスコープ（パーサー・基本制御構文）
  に対して実装コストを最小化できる
- 正規化の判定が「数値トークンへの空白なし隣接」という字面のみで
  決まるため、辞書の状態に一切依存しない。パーサーの単純さを
  優先するUmorの一貫した設計方針（4.3節）とも整合する
- `番目`は独立ワードとして扱われるため、`（）`の脱糖衣（ADR-0003）
  の着地点としてもそのまま利用できる

**トレードオフとして受け入れるもの**：

- `5000円 + 3ドル`のような単位不整合はフェーズ1では検出できない
  （Mind同様、単位系の管理はプログラマの責任になる）
- 助数詞による型安全性というアイデア自体は失われたわけではなく、
  フェーズ2で型システムを導入する際に、宣言構文・Value Object化と
  あわせて再設計する必要がある
