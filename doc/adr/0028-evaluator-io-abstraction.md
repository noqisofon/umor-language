# ADR-0028: 評価器の出力I/O抽象化（バッファ化）

## Status

Proposed

## Context

ADR-0027（Umor Playgroundの初期スコープ）で、Playground実装は
本ADRの確定・実装を前提とする依存関係にあると記録した。

現在の評価器は、`表示する`等の出力系ワードの実装で、Rustの
標準出力（`println!`相当）に直接書き込んでいると考えられる。
CLI（ファイル実行・REPL）ではこれで問題ないが、WASM化して
ブラウザ上で動かすPlaygroundでは、標準出力という概念自体が
存在しない。ブラウザ側では「評価器が生成した出力文字列を
JS側で受け取り、DOM上の出力欄に表示する」という形に変える
必要がある。

つまり、出力先を「標準出力に固定」ではなく「差し替え可能な
シンク（sink）」として抽象化する設計変更が必要になる。この
変更はCLI・WASM両方の実行経路に影響するため、Playground本体の
実装（ADR-0027）とは切り離し、評価器コア側の設計判断として
独立に検討する。

## Decision

評価器の出力先を、Rustのtraitによる抽象化で差し替え可能にする。

```rust
trait OutputSink {
    fn write(&mut self, s: &str);
}
```

- CLI向けの実装：標準出力にそのまま書き込む`StdoutSink`
  （内部的に`println!`相当を呼ぶだけの�diaper薄いラッパー）。
- WASM向けの実装：文字列をバッファ（`String`または`Vec<String>`）
  に蓄積する`BufferSink`。Playground側はWASM呼び出しの完了後、
  このバッファの内容をJSに返して出力欄に表示する。

評価器（インタプリタ本体）は`OutputSink`を実行時に1つ受け取り、
`表示する`等の出力系ワードはすべてこのtraitのメソッド経由で
書き込む。評価器の構築時（`Interpreter::new`相当）に
`Box<dyn OutputSink>`または型パラメータとして注入する形にし、
出力先の選択はエントリポイント（CLIのmain、WASMのエクスポート
関数）側の責務とする。

**エラー出力との関係**：本ADRは`表示する`系の標準出力相当のみを
対象とする。パニック・実行時エラーの扱い（ADR-0027で触れた
`catch_unwind`によるパニック捕捉）は別の関心事として扱い、
本ADRのスコープには含めない。ただし、エラーメッセージも
最終的にはPlayground側の出力欄（またはエラー欄）に表示する
必要があるため、実装時に両者の接続方法（同じ`OutputSink`を
使うか、別チャネルにするか）を確認する。

**既存コードへの影響**：`表示する`等の出力系ワードのネイティブ
実装箇所（`register_builtins`内、あるいは相当する評価器コード）
を、直接`println!`を呼ぶ形から`OutputSink`経由に書き換える。
影響範囲は出力系ワードに限定され、スタック操作・制御フロー系の
ワードには影響しない見込み。

## Consequences

**得られるもの**：

- WASM化されたPlaygroundとCLIが同じ評価器コードを共有しつつ、
  出力先だけを差し替えられるようになる。ADR-0027で決定した
  「WASM化により挙動を完全一致させる」方針を実際に成立させる
  ための土台になる。
- 将来、出力先をさらに増やす場合（例：テストでの出力キャプチャ、
  ログファイルへの出力）も同じ抽象化の上で対応できる。

**トレードオフとして受け入れるもの**：

- 出力系ワードの実装箇所を横断的に書き換えるリファクタリング
  コストが発生する。既存のテスト（101件、ADR-0012時点）が
  出力を直接アサートしている場合、その取得方法も見直しが
  必要になる可能性がある。
- 評価器の構築シグネチャに`OutputSink`の注入が加わるため、
  評価器を生成しているすべての箇所（CLI main、REPL、テスト
  ヘルパー）を洗い出して更新する必要がある。
- `Box<dyn OutputSink>`による動的ディスパッチはごく僅かな
  オーバーヘッドを持つが、Umorの実行速度要件を考えると
  無視できる範囲と見込まれる。

## 宿題

- パニック捕捉（`catch_unwind`）との接続方法は未検討。エラー
  メッセージを`OutputSink`に統合するか別チャネルにするかは
  Playground実装時に決定する。
- 既存101件のテストのうち、出力を直接アサートしているものが
  どの程度あるか未調査。書き換え範囲の見積もりが必要。
- `BufferSink`のバッファサイズ上限（無限ループで出力し続けた
  場合の対処）は未検討。Playground側でのタイムアウト・実行制限
  と合わせて別途検討が必要になる可能性がある。
