# ADR-0003: `（）`は独立した評価規則を持たず、`番目`への脱糖衣として扱う

## Status

Accepted

## Context

配列・コレクションへのインデックスアクセスをどう表現するかについて、
検討の過程で2つの案が上がった。

**案A（当初採用・後に撤回）**：`（）`をForthに近いスタックベースの
独立した評価規則として設計する。「`（）`の中身を1つの式として評価し、
その結果をpushしてから外側のワードを呼ぶ」というグルーピング構文とし、
多次元配列は`（）`を連続させる（カリー化スタイル）ことで表現する。

```umor
売り上げ（回数 番目）
ダンジョンマップ（X軸座標）（Y座標）
```

この案では`（）`自体がAST上に独立したノードとして存在し、
「アリティNの処理単語呼び出し」という評価規則をパーサー・VMの
両方が独自に持つ必要があった。

**案B（採用）**：添字アクセスは、そもそも`（）`という専用構文なしで、
標準ライブラリワード`番目`（ADR-0002で確定）を使った通常の
分かち書きとして表現できる。

```umor
売り上げの 1 番目
```

`（）`はこの表現に対する**構文糖衣**としてのみ存在させ、
パース段階で通常の分かち書きへ機械的に展開（脱糖衣）する。

```
売り上げ（1）
  ↓ 脱糖衣
売り上げの 1 番目
```

多次元配列も、脱糖衣を繰り返し適用するだけで同じ原理で説明できる。

```
ダンジョンマップ（X軸座標）（Y座標）
  ↓ 脱糖衣（1段目）
ダンジョンマップの X軸座標 番目（Y座標）
  ↓ 脱糖衣（2段目）
ダンジョンマップの X軸座標 番目の Y座標 番目
```

この場合、VM/IRのレベルには`（）`という概念自体が存在しなくなり、
IRに現れるのは通常のワード呼び出し列だけになる。

## Decision

`（）`は独立した評価規則を持たない。パース段階で
`〈式〉の 〈式〉 番目`という通常の分かち書きへ機械的に脱糖衣する、
純粋な構文糖衣として実装する。

- `（）`の中に数値リテラルを直接書く場合、脱糖衣後は
  `〈値〉の 〈数値〉 番目`という、数値と`番目`の間に必ず空白が
  入る形に展開される。そのため、ADR-0002の正規化規則
  （数値への空白なし隣接の畳み込み）と衝突することはない
- 脱糖衣をレキサー/パーサーのどちらの段階で行うか
  （字句解析後の別パスにするか、パーサー内で直接展開するか）は
  実装時に決定する未解決事項として残す

## Consequences

**得られるもの**：

- VM/IRが扱う概念の種類が増えない。「アリティNの処理単語呼び出し」
  という独自の評価規則をパーサー・VMの両方に持たせる必要がなく、
  すべてが通常のワード呼び出し列に帰着する
- 多次元配列アクセスも新しい評価規則を必要とせず、脱糖衣の
  繰り返し適用だけで説明がつく
- `番目`が通常ワードである（ADR-0002）ことの直接の帰結として
  自然に導かれる設計であり、概念間の依存関係がシンプルになる

**トレードオフとして受け入れるもの**：

- `（）`の脱糖衣処理をどのフェーズ（レキサー後の別パス／パーサー内）
  で行うかは未確定のまま残っており、実装時に決定する必要がある
- `（）`が糖衣構文であることを利用者が意識しなくても使えるようには
  するが、エラーメッセージ等で脱糖衣後の形（`の`・`番目`を使った形）
  が露出した場合、利用者が混乱しないような配慮は別途必要になる
  可能性がある（本ADRのスコープ外、実装時の課題）
